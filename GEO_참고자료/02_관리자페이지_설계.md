# GEO 관리자 페이지 설계 (샘플 치환본)

> **용도:** 이 문서를 AI(바이브코딩)에 그대로 주고 "이대로 관리자 페이지를 만들어줘"라고 지시할 수 있는 **완성형 청사진**.
> **적용 범위:** 지역 기반 비즈니스 전반 (병의원·요양병원·한의원 / 학원·법률·미용·헬스 등 "지역+업종" 키워드로 고객을 모으는 모든 업종).
> **근거:** 실제 운영 admin 2곳(샘플요양병원·샘플한의원) 직접 분석 + 우수사례(샘플치과) 프론트 실측 + 「홈페이지 GEO 최종분석」(01 문서) + 범용 관리자 페이지 플레이북(운영·보안 원칙, 페이지 관리·용어사전·로그 모듈 통합). (실측 원본은 Payload CMS였으나, 이 설계는 스택 무관한 **필드·구조·운영 원칙**을 뽑아낸 것이다.)
> **기술 전제 (2026-07-22 확정):** **Supabase(Postgres + Auth + RLS) + SSR 프론트엔드(Next.js)**. 관리자 UI는 이 설계서를 청사진으로 직접 구현하고, 데이터/JSON-LD 저장·제공은 [04_supabase_참고구현](04_supabase_참고구현/)을 따른다. (구버전은 Payload CMS 전제였음 — [06 결정 변경 이력](06_인증_저장소_세팅가이드.md) 참조.)
> **익명화:** 업장 상호·인명·주소·전화·도메인은 전부 샘플 치환됨(README 치환표 참조).

## 📐 설계 3대 원칙 (이걸 어기면 GEO가 작동 안 함)

1. **글 1편 = 본문 + 메타 + JSON-LD 한 세트.** 콘텐츠와 구조화 데이터를 분리하지 않는다. 발행 시 항상 함께 생성·저장.
2. **비즈니스 정보는 전역(Global) 1곳에서 관리 → 모든 글·페이지 JSON-LD에 자동 주입.** 글마다 주소를 다시 적지 않는다.
3. **AI 크롤러 레이어(robots.txt / llms.txt)를 admin에서 직접 관리.** 경쟁사 전부 비어 있는 영역 = 최대 선점 기회.

> **봇 우선 원칙:** 관리하는 모든 데이터는 "사람 눈에 예쁜가"가 아니라 **"봇이 코드로 정확히 읽는가"** 기준으로 설계한다.

### 운영 6대 원칙 (어떤 스택이든 공통)

1. **권한은 데이터 계층이 최종 판별.** 화면의 `requireAdmin()`류 가드는 UX용 1차 방어일 뿐 — 진짜 방어는 데이터 계층의 접근 제어(**Supabase RLS 정책**). 프론트를 뚫어도 데이터가 안 나와야 한다.
2. **관리자 미리보기 = 실제 방문자 화면.** 모방 컴포넌트 금지 — 공개 페이지와 같은 렌더러·같은 CSS를 재사용하고, "사이트에서 보기 ↗" 버튼으로 실제 페이지에 연결한다.
3. **파괴적 행동(삭제·발송)은 체크박스 confirm 후 실행.**
4. **저장 버튼은 진행 상태 표시** ("저장 중…") — 느린 회선에서 이중 클릭 방지.
5. **운영자는 비개발자.** 모든 화면에 한국어 안내 문구, 전문용어엔 한 줄 설명.
6. **콘텐츠는 초안(draft) → 검토 → 공개(published) 2단계.** AI가 초안을 쓰고 사람이 승인한다. (7장 발행 워크플로와 동일 사상)

### 이 설계의 실측 근거 — 방법론 ↔ 실제 구현 매핑

GEO 방법론 6대 기술 요소가 실측 admin 2곳에서 어디까지 구현돼 있었는지 대조한 결과 (= 이 설계서가 무엇을 유지하고 무엇을 새로 추가하는지의 근거):

| 방법론 (01 문서) | 실측 admin 구현 여부 | 이 설계서의 결정 |
|-----------------|:---:|------|
| 5.1 robots.txt (AI 크롤러 Allow) | ❌ 미구현 | **관리 메뉴로 추가** (3.4) |
| 5.2 llms.txt | ❌ 미구현 (비교군 전부 부재) | **관리 메뉴로 추가 = 선점 기회** (3.5) |
| 5.3 JSON-LD 구조화 데이터 | ✅ 글마다 `Structured Data` 필드 | **유지 — 단, 자동 생성으로 고도화** (2.2) |
| 5.4 푸터 키워드 페이지 | 🔶 페이지 형태로만 운영 (관리 메뉴 없음) | **"키워드 페이지" 컬렉션으로 정식화** (3.2) |
| 5.6 FAQ형 콘텐츠 | ✅ JSON-LD 안에 FAQPage 포함 | **FAQ를 독립 관리 단위로 분리** (3.3) |
| 6장 블로그 자동 발행 | ✅ 규칙적 대량 발행으로 정황 확인 | **외부 원글 → 변환 → 발행 연동 지점 신설** (7) |

**실측에서 확인된 핵심 공백 3가지** (= 신규 GEO 홈페이지에서 반드시 메꿔야 할 것):
1. **robots.txt / llms.txt 관리 화면** — 실측 2곳 모두 admin에서 관리 안 됨. 경쟁사 실측에서도 전부 부재 → **가장 큰 선점 기회**
2. **사이트 전역(Global) 비즈니스 정보** — 글마다 JSON-LD에 업장 정보를 반복 삽입 중 (중복). 전역 1곳 관리 → 자동 주입 구조가 없음
3. **비즈니스 실제 정보 관리** (영업시간·오시는 길·구성원·문의 접수) — 블로그 발행기로는 완성됐으나 "홈페이지"로서의 정보 관리 메뉴가 없음

→ 이 3가지가 그대로 설계 3대 원칙과 ★신규 메뉴(GEO 엔진·비즈니스 정보)의 근거다.

## 🏗️ 배포 아키텍처 — 관리자(Railway 등)와 프론트(Vercel)를 나누는 이유

> 실측한 두 사이트가 실제로 쓴 구조이자, 신규 GEO 홈페이지에 권장하는 표준.

### Supabase란? (관리자·DB 스택)

**관리형 Postgres + Auth + RLS + 스토리지를 한 번에 주는 백엔드 서비스.** 테이블(schema.sql)만 정의하면 DB·인증·행 단위 보안(RLS)을 제공한다. Payload와 달리 **관리자 UI는 자동 생성되지 않으므로 이 설계서를 청사진 삼아 직접 구현**하되, 그 대가로 UI를 100% 원하는 대로 만들 수 있다. GEO 로직(JSON-LD 조립·자동발행)은 [04_supabase_참고구현](04_supabase_참고구현/)의 코드로 얹는다.

### 분리 구조 (프론트 / DB / 스케줄러)

```
        일반 방문자 / AI 봇                          사장님 / 관리자
              │                                        │
              ▼                                        ▼
┌──────────────────────────────┐        ┌──────────────────────────────┐
│   Vercel  (프론트 + 관리자 UI) │  쿼리  │   Supabase  (Postgres+Auth)   │
│  · 방문자가 보는 홈페이지         │ ◀────▶ │  · 글·비즈니스·문의 데이터 저장   │
│  · 블로그 글 표시               │anon/svc│  · RLS로 published만 공개       │
│  · ★JSON-LD·메타·robots를      │  role  │  · 관리자 인증(Auth)            │
│    SSR로 <head>에 주입          │        │  · 관리형 — 서버 직접 운영 불필요 │
│  · Next.js (관리자 화면 포함)    │        │                               │
└──────────────────────────────┘        └──────────────────────────────┘
              │                                        ▲
              │              ┌──────────────────────────────┐
              └──────────────│  Railway (자동발행 스케줄러)   │
               (스케줄러가     │  · 네이버 폴링·리라이팅 상주작업 │
                Supabase에    │  · service_role로 Supabase write│
                write)        └──────────────────────────────┘
```

### 왜 이렇게 나누는가

| | Vercel (프론트+관리자UI) | Supabase (DB·Auth) | Railway (스케줄러) |
|---|---|---|---|
| 역할 | 페이지 렌더 + 관리자 화면 | 데이터·인증·RLS | 상주 폴링·자동발행 |
| 이유 | 전 세계 빠른 배포 | 관리형이라 DB 서버 운영 불필요 | 서버리스로 못 하는 상주 작업 |

> Payload 시절엔 "관리자 UI + DB"가 Railway 한 몸이었지만, Supabase는 **DB를 관리형으로 떼고(운영 부담↓)**, 관리자 UI는 Vercel 프론트에 함께 얹는다. Railway는 **스케줄러 하나만** 남는다.

### GEO 관점에서 결정적인 점 (스택 무관 — 변함없음)

- **AI 봇이 실제로 읽는 페이지는 프론트(Vercel)에서 나온다.** → JSON-LD·메타·robots.txt는 **반드시 프론트에서 SSR로 `<head>`에 박혀야** 봇이 읽는다. (Supabase/Payload 무관)
- **DB(Supabase)는 봇이 직접 안 본다.** "전역 비즈니스 정보(3.1)"는 `settings_business`에 저장하고, 프론트가 쿼리해 모든 글 JSON-LD에 자동 주입한다.

### ★ 백엔드 "상시 서버"가 반드시 필요한 이유 — 블로그 자동 발행

**네이버 블로그 글 → 자동 각색 → 홈페이지 포스팅** 파이프라인(7장)이 사람 개입 없이 돌아야 한다. 이 폴링·스케줄 발행은 **항상 켜진 서버(Railway)** 가 담당하고, 결과는 **Supabase에 service_role로 저장**한다:

- Vercel 서버리스는 요청 시에만 켜지므로 "주기적 네이버 확인 + 발행 스케줄 관리" 상주 작업에 부적합 → Railway 필요.
- 단, Payload 때와 달리 **Railway엔 DB가 없다.** 데이터는 Supabase가 보유하고 Railway는 스케줄러 코드만 실행.
- 발행량은 **매일 5~6개(관리자에서 세팅)** — 상세는 7.2.

### 선택 가이드

| 상황 | 권장 구조 |
|------|----------|
| 블로그를 자주·대량 발행 + 비개발자도 글 작성 (= GEO 핵심) | ✅ **Vercel(프론트+관리자UI) + Supabase(DB) + Railway(스케줄러)** |
| 글이 거의 없는 정적 회사소개 사이트 | 스케줄러 불필요. Vercel + Supabase만 |
| 회원 기능(유형②)·결제(유형③) | 같은 Supabase에 Auth 소셜로그인·결제 테이블 추가 ([06 CP-0](06_인증_저장소_세팅가이드.md)) |

> **결론:** GEO 홈페이지는 "대량 콘텐츠 발행"이 본질 → 스케줄러(Railway) 필요. 단, **robots/llms/JSON-LD가 프론트에서 SSR로 출력되는지 반드시 확인.**

## 🗂️ 관리자 페이지 전체 구조 (메뉴 맵)

> 범례: ★신규 = 실측한 실제 admin 2곳엔 없던, GEO 홈페이지에 **반드시 추가**할 기능.

```
GEO 관리자페이지
│
├── 📊 대시보드 ─────────── GEO 건강점수·발행현황·인기글·미접수문의·점검알림
│
├── 📝 콘텐츠
│   ├── 블로그 글 (Blogs) ── 핵심 콘텐츠 공장. 글 1편 = 본문+메타+JSON-LD 한 세트
│   ├── 페이지 관리 ★ ────── 세부페이지(인사말·서비스·오시는 길…) 생성·편집·삭제 (2.6)
│   ├── 용어사전 ★ ───────── 전문용어를 쉬운 비유로. DefinedTerm 스키마 (2.7)
│   ├── 사례·후기 ────────── 치료/시공/승소 사례. 업종별 광고 규정 주의 (2.8)
│   ├── 카테고리 ─────────── 글 분류 (계층형: 상위/하위)
│   ├── 태그 ─────────────── 글 꼬리표
│   └── 추천/인기글 ───────── 메인에 노출할 글 수동 지정
│
├── 🎯 GEO 엔진  ★신규·핵심
│   ├── 전역 비즈니스 정보 ── 상호·주소·좌표·전화를 한 곳에 → 모든 글 JSON-LD에 자동 주입
│   ├── 키워드 전용 페이지 ── "지역+돈되는 키워드"마다 1페이지, 푸터에 작은 링크로 배치
│   ├── FAQ 관리 ─────────── Q&A를 글/페이지에 연결 → FAQPage 스키마 자동 생성 (AEO 핵심)
│   ├── robots.txt 관리 ──── AI 크롤러 허용 토글 + 사이트맵 줄 + 미리보기
│   ├── llms.txt 관리 ────── LLM 전용 사이트 안내 파일 생성
│   ├── sitemap 설정 ─────── 자동 생성 + priority/주기 + punycode + canonical
│   └── 자동 발행 설정 ★ ─── 네이버 블로그 연동 + 일일 발행 개수(기본 5~6) + 자동/검수 모드 (7.2)
│
├── 🏢 비즈니스 정보  ★신규
│   ├── 기본 정보 ────────── 상호·주소·연락처·영업시간·사업자번호 (전역정보와 연동)
│   ├── 구성원/전문가 ────── 의료진·강사 등 → author 연결. ★author.sameAs(LinkedIn 등) 신원 검증
│   ├── 서비스/품목 안내 ─── 진료과목·강좌·메뉴 등 제공 항목
│   ├── 오시는 길 ────────── 지도 임베드 + 좌표 + 주차/대중교통 (로컬 SEO 핵심)
│   └── 문의 접수함 ──────── 홈페이지 문의폼 상담 관리 (신규/처리중/완료)
│
├── 🖼️ 미디어 ───────────── 이미지·파일 라이브러리 + alt 텍스트 (이미지 SEO)
│
└── ⚙️ 운영
    ├── 사용자/권한 ──────── 역할 분리 (최고관리자/콘텐츠/비즈니스/뷰어)
```

### 2.2 JSON-LD 자동 생성 규칙 ★

글 저장 시 아래 3종 스키마를 `@graph`로 묶어 **자동 생성**한다 (실측 사이트의 실제 구현 형태):

1. **`BlogPosting`** ← title, excerpt, publishedAt, author(실명·직책)
2. **`[업종]Business`** ← **전역 비즈니스 정보(3.1)에서 자동 주입** (상호·주소·좌표·전화·영업시간). 업종별 @type: 병원=`MedicalClinic`/`Hospital`, 일반=`LocalBusiness`
3. **`FAQPage`** ← 이 글에 연결된 FAQ 자동 변환

**실측된 실제 JSON-LD 예시** (샘플한의원의 글 1편에서 추출한 구조, 값은 샘플 치환):

```json
{
  "@context": "https://schema.org",
  "@graph": [
    {
      "@type": "BlogPosting",
      "headline": "조금만 걸으면 다리가 터질 듯 저린 이유 — B시 C동 한의원에서 보는 척추관 협착증",
      "description": "...척추관 협착증은 좁아진 신경 통로와 혈류 정체가...",
      "author": { "@type": "Person", "name": "홍길동 원장" },
      "inLanguage": "ko"
    },
    {
      "@type": "MedicalClinic",
      "name": "샘플한의원",
      "geo": { "@type": "GeoCoordinates", "latitude": 37.000, "longitude": 127.000 },
      "address": {
        "@type": "PostalAddress",
        "streetAddress": "샘플로 123 샘플빌딩 5층",
        "addressLocality": "B시 ○○구",
        "addressRegion": "○○도",
        "addressCountry": "KR"
      },
      "telephone": "000-0000-0000",
      "openingHours": ["Mo Tu We Th Fr 08:30-20:00", "Sa 08:30-13:00"]
    },
    {
      "@type": "FAQPage",
      "mainEntity": [
        { "@type": "Question", "name": "척추관 협착증은 꼭 수술해야 하나요?",
          "acceptedAnswer": { "@type": "Answer", "text": "..." } }
      ]
    }
  ]
}
```

이 한 덩어리에 GEO 3대 무기가 모두 들어 있다: ① BlogPosting(글+저자 실명 = E-E-A-T) ② [업종]Business(위경도+주소+전화 = 지역 타겟팅) ③ FAQPage(Q&A = AEO 직접 인용).

> **자동화가 핵심.** 관리자가 JSON을 손으로 짜는 게 아니라 필드 입력 → 시스템이 조립. 단, **수동 편집(override)도 허용**해 예외 대응.
> **주입 시점:** 반드시 **SSR `<head>`에 직접 주입.** 클라이언트 렌더링이면 봇이 첫 응답에서 못 읽음.

### 2.6 페이지 관리 — 세부페이지 생성·편집·삭제 ★ (홈페이지의 몸통)

> 운영자가 **코드 수정 없이** 서브페이지(인사말·구성원 소개·서비스 안내·비급여/가격 안내·오시는 길·업무분야 상세 등)를 **생성하고 · 내용을 조정하고 · 내리는** 구조.

**설계 원칙 — "자유 빌더"가 아니라 "섹션 카탈로그 조립":**
- 임의 레이아웃을 드래그로 조립하는 자유 빌더는 만들지 않는다 (유지비 함정).
- 개발자가 **섹션 종류(kind) 카탈로그**를 정의하고, 운영자는 종류를 골라 **순서를 조립하고 내용만 채운다.** 새 레이아웃이 필요하면 개발자가 kind를 하나 추가한다.

**데이터 모델 (2계층):**

| 계층 | 필드 |
|------|------|
| 페이지 (`Pages` 컬렉션) | `slug`(unique) · `title` · `metaDescription` · `navLabel` · `showInNav` · `navOrder` · `isPublished`(초안→공개) |
| 섹션 (페이지 안의 반복 블록) | `kind`(`hero` \| `text` \| `image_text` \| `cards` \| `cta` \| `faq` \| `map` …) · `title` · `body`(리치텍스트/마크다운) · `image` · `data`(kind별 추가 필드) · `sortOrder` · `isVisible` |

> **Supabase 매핑:** 이 "kind 카탈로그 조립" 모델은 `site_pages` + `page_sections` 2테이블(FK) + RLS로 구현한다. 각 섹션 행에 `kind` 컬럼 + `data` JSONB(그 kind의 필드 묶음)를 두면 블록형 페이지 빌더가 된다.

**공개 렌더링:**
- 동적 라우트 `/(pages)/[slug]` — 미공개면 404, 섹션을 sortOrder대로 **kind별 렌더러 컴포넌트**로 그림
- `generateMetadata`: title·metaDescription. 예약 slug(admin·login·api…)는 생성 시 차단
- 헤더/푸터 네비게이션: `showInNav=true`인 공개 페이지를 navOrder로 읽어 **자동 메뉴 구성**
- JSON-LD: 전역 비즈니스 정보(3.1) + Breadcrumb 자동 주입, 연결 FAQ 있으면 FAQPage도

**관리자 UX:**
- 목록: 생성(제목+slug만으로) / 공개·초안 토글 / 네비 노출 토글 / 삭제(confirm 체크박스) / "사이트에서 보기 ↗"
- 편집: 기본 정보 + **섹션 리스트** (kind 선택 드롭다운 → kind별 입력 폼 / 드래그 정렬 / 표시·숨김 / 삭제)
- 본문 이미지: 붙여넣기·드래그 → 미디어 라이브러리(5장) → 삽입
- **실시간 미리보기:** 공개 페이지와 같은 kind 렌더러를 그대로 재사용 (운영 원칙 2)
- **✨ AI 초안:** 페이지 제목+업종 입력 → 섹션 구성(kind 배열)과 각 섹션 문구 초안 제안
- **삭제/이동 가드 (GEO 필수):** 네비 노출 중인 페이지 삭제 시 경고. **slug 변경 시 구 slug → 새 slug 리다이렉트 기록**(`page_redirects`) — 이미 색인·AI 인용된 URL의 유입을 보호

> **키워드 전용 페이지(3.2)와의 관계:** 3.2는 "지역+키워드" GEO 타겟 페이지(푸터 노출 + AEO 포맷 + 정직성 체크 강제), 이 모듈은 일반 안내 서브페이지. **같은 섹션 렌더러를 공유하되 컬렉션은 분리**해 각자의 규칙을 유지한다.

### 2.7 용어사전 (Glossary) ★ GEO 핵심 — 전문직에 특히 강력

> 고객이 검색하는 전문용어("임플란트 골이식", "가압류 뜻" 등)를 **쉬운 비유로 풀어주는 공개 사전.** AI 검색이 "쉬운 설명"을 인용하기 가장 좋은 형태.

| 필드 | 설명 |
|------|------|
| `slug`(unique) / `term` / `termEn` | 용어 (한/영) |
| `category` | 분류 |
| `oneLiner` | **한줄 설명 (일상 비유)** — AI 인용 1순위 |
| `description` | 상세 설명 |
| `examples` | 예시 |
| `relatedSlugs` | 관련 용어 (내부링크) |
| `isPublished` / `sortOrder` | 공개·정렬 |

- 공개: `/glossary` + `/glossary/[slug]` — 메타데이터 + **DefinedTerm JSON-LD** + 내부링크
- **✨ AI 초안:** 단어+카테고리만 입력 → LLM(JSON mode)이 한줄설명·상세·예시·관련 용어를 채움. **기존 slug 목록을 프롬프트에 제공**해 실재하는 용어만 관련어로 연결
- 프롬프트 페르소나: "고객에게 설명하는 친절한 전문가. 진단·법률자문으로 오해될 단정 표현 금지, '개인차가 있으니 상담 필요' 뉘앙스 유지"
- **05 참고구현과의 연결:** 리라이팅 `geo` 모드가 글마다 생성하는 `glossary`(정의+쉽게 2층)를 이 컬렉션에 누적하면 사전이 자동으로 자란다

### 3.1 사이트 전역 비즈니스 정보 (Global) ★

> **모든 글·페이지 JSON-LD에 자동 주입되는 단일 소스.** 글마다 주소를 반복 입력하던 비효율 제거.

| 필드 | 타입 | JSON-LD 매핑 |
|------|------|------|
| 상호명 | text | `name` |
| 비즈니스 유형 | select | `@type` (LocalBusiness/MedicalClinic/Hospital 등) |
| 도로명 주소 | text | `address.streetAddress` |
| 지역(시/구) | text | `address.addressLocality` |
| 광역(도/시) | text | `address.addressRegion` |
| 우편번호 | text | `address.postalCode` |
| 국가 | text(KR) | `address.addressCountry` |
| **위도 / 경도** | number | `geo.latitude` / `geo.longitude` ← **로컬 검색 핵심** |
| 대표 전화 | text | `telephone` |
| 영업/진료시간 | repeater | `openingHours` (예: "Mo-Fr 08:30-20:00") |
| 대표 URL | text | `url` (한글도메인은 **punycode 자동 변환** 표기) |
| 로고 | upload | `logo` |
| 전문 분야 | repeater | `MedicalSpecialty` 등 |

### 3.2 키워드 전용 페이지 (Landing / Footer Pages) ★

> "지역+돈 되는 키워드"마다 **전용 페이지 1개**를 만들어 **푸터 작은 링크로 배치.**

| 필드 | 타입 | 설명 |
|------|------|------|
| 타겟 키워드 | text | 예: "B시 한의원", "임종기 요양병원" |
| `slug` | text | 전용 URL |
| 페이지 제목/H1 | text | **인텐트 질문형 권장**: "○○ 어떻게 선택해야 할까요?" |
| 본문 구조 | rich text | **대상 → 선택기준 → 특징 → FAQ → CTA** (AEO 최적 포맷) |
| 연결 FAQ | relationship | FAQPage 스키마 자동 생성 |
| 푸터 노출 | checkbox | 푸터 키워드 링크에 표시 여부 |
| JSON-LD | 자동 | FAQ + Breadcrumb + 비즈니스 |
| 정직성 확인 | checkbox | **허위·과장 없음 검수** (클로킹 패널티 방지) |

### 3.3 FAQ 관리 ★

> AI가 가장 잘 인용하는 포맷(AEO). 글·페이지에 연결 → FAQPage 스키마 자동 생성.

| 필드 | 타입 | 설명 |
|------|------|------|
| 질문 | text | `Question.name` |
| 답변 | textarea | `acceptedAnswer.text` |
| 연결 대상 | relationship | 어느 글/페이지에 붙일지 |
| 노출 순서 | number | 정렬 |

> **정합성 메모 (05 문서의 AEO 지침과 함께 읽을 때):** 구글의 FAQ **리치 결과**(검색결과 아코디언)는 2026-05 폐지됐다. 즉 FAQPage 스키마의 목적은 이제 구글 리치결과가 아니라 **AI 답변엔진(ChatGPT·Perplexity 등) 인용**이다 — 이 설계의 FAQ 자동 스키마는 그 용도로 유지하되, 리치결과만 노리고 남발하지 말고 실제 사용자에게 유효한 Q&A만 담는다.

### 3.4 robots.txt 관리 ★ (경쟁사 공백 = 선점 기회)

| 기능 | 설명 |
|------|------|
| AI 크롤러 토글 | 최소 9종: GPTBot, OAI-SearchBot, ChatGPT-User, ClaudeBot, anthropic-ai, Google-Extended, PerplexityBot, Applebot-Extended, CCBot (우수사례는 Grok·DeepSeek·Copilot 등 30종+) |
| 일반 규칙 | Allow/Disallow 경로 편집 |
| 트래킹 파라미터 차단 | `/*?utm_source`, `/*?ref=` 등 (크롤 버짓 보호) |
| Sitemap 줄 | sitemap URL 자동 삽입 |
| 미리보기 | 생성될 robots.txt 실시간 확인 |

### 3.5 llms.txt 관리 ★ (신규 규약 = 가장 큰 선점 기회)

| 필드 | 자동/수동 | 설명 |
|------|------|------|
| 사이트명(H1) | 전역에서 자동 | `# 상호명` |
| 한 줄 요약 | text | `> 인용문` |
| 섹션별 핵심 페이지 | 자동 + 수동 | `## 섹션` + `[제목](URL): 설명` 목록 |
| 출력 미리보기 | 자동 | `/llms.txt` 마크다운 렌더 |

> 우수사례 수준: Quick Facts(상호·사업자번호·대표·주소·전화·SNS·영업시간)를 키-값으로 + Leadership(전문가 실명·자격) + 서비스별 URL 매핑 + `llms-full.txt` 별도 운영.

### 3.6 sitemap 설정 ★

| 기능 | 설명 |
|------|------|
| 자동 생성 | 모든 발행 글·페이지 포함 |
| Priority/주기 | 홈·핵심랜딩 1.0/weekly, 블로그 daily, 안내 monthly |
| punycode 처리 | 한글도메인 자동 변환 |
| canonical 정규화 | 후행 슬래시·쿼리 중복 방지 |

> 우수사례 수준: 인덱스 아래 분야별 분리(main/area/백과사전/다국어/컬럼/케이스). 지역 페이지 88개 + 업종 백과사전 862개 = 주제 권위(Topical Authority) 대량 확보.

### 3.7 GEO 콘텐츠 3종 세트 + 내부링크 "지식망" 규칙 ★

AI 검색(ChatGPT·Perplexity)과 구글 모두를 겨냥한 공개 콘텐츠 파이프라인:

| # | 콘텐츠 | 타깃 질문 | JSON-LD |
|:-:|--------|-----------|---------|
| 1 | **용어사전** (2.7) | "○○ 뜻", "○○이 뭔가요" | `DefinedTerm` |
| 2 | **FAQ** (3.3) | "○○ 얼마나 걸려요/아파요/비용은" | `FAQPage` |
| 3 | **칼럼/블로그** (2.1) | "지역+증상/이슈" 롱테일 | `BlogPosting` |

- **내부링크 규칙:** 칼럼 ↔ 용어사전 ↔ FAQ를 related로 **상호 연결** — AI가 사이트를 하나의 '지식망'으로 인식(주제 권위 신호). 키워드 전용 페이지(3.2)와 페이지 관리(2.6)의 페이지들도 이 망에 연결한다.
- 모든 AI 초안은 **"검토 후 공개"** (운영 원칙 6) — 전문직은 틀린 정보가 곧 리스크.

## 4. 🏢 비즈니스 정보 ★신규 (실측 admin 2곳에 없던 영역)

### 4.1 기본 정보
3.1 전역 정보와 연동 (상호·주소·연락처·영업시간·사업자번호 등).

- **법적 필수 푸터 자동 구성:** 상호·대표자·사업자등록번호·주소·연락처·(통신판매 시)통신판매업신고 + 이용약관·개인정보처리방침 링크. 푸터 컴포넌트가 이 전역 정보를 읽어 **코드 수정 없이** 반영되게 한다.

### 4.2 구성원/전문가 (Staff/Experts) ★작성자 신뢰도 강화

> 의료진·강사·변호사 등. **author로 연결 → E-E-A-T 신호.**
> (보강 근거: 우수사례 실측 — robots/llms/sitemap은 만점이나 **작성자 신원 연결만 비어 있던** 사례. 01 문서 8.7 참조)

| 필드 | 타입 | JSON-LD 매핑 / GEO 역할 |
|------|------|------|
| 이름 / 직책 | text | `author.name` / `author.jobTitle` |
| 사진 | upload | 프로필 |
| 전문분야·경력 | textarea | `author.description` (신뢰도) |
| 학력 | text | `author.alumniOf` (학력 엔티티화 → E-E-A-T) |
| 소속 | relationship | `author.worksFor` (전역 비즈니스 연결) |
| **개인 프로필 URL** | text | `author.url` — **블로그 홈이 아닌 "이 구성원 전용 페이지"로 지정** |
| **★ 외부 신원 링크 (sameAs)** | repeater | `author.sameAs` — **LinkedIn·논문·유튜브 등 본인 운영 권위 프로필.** AI/구글이 동명이인과 구별하고 실존 전문가로 검증하는 핵심 신호 |

> **★ sameAs 규칙 (작성자 E-E-A-T의 핵심):**
> - 글의 `author` 객체에 **반드시 본인이 운영하는 외부 프로필(LinkedIn 우선)** 을 `sameAs` 배열로 연결. 조직(Organization) sameAs와 **별개로** 작성자 개인(Person) sameAs를 둔다.
> - ⚠️ **"공유(Share) 버튼"과 혼동 금지.** 화면의 LinkedIn/페북 공유 아이콘은 방문자용 위젯일 뿐, 봇은 신뢰 신호로 쓰지 않는다. 신뢰 신호는 오직 **JSON-LD `author.sameAs`**.
> - ⚠️ **실존·본인 소유 프로필만.** 가짜/타인 프로필은 스팸 신호로 역효과. 없으면 만들어 경력을 채운 뒤 연결.

> **★ 리스크 가드 — 작성자 동일성 검수 (필수 체크):**
> 화면에 표기되는 작성자와 JSON-LD `author.name`이 **반드시 일치**해야 한다. (우수사례 실측에서 화면="김철수" vs JSON-LD="이영희" 불일치 발견 → AI가 작성자 오인식.)
> → 발행 워크플로(7장)에 **`authorIdentityMatch`(화면↔JSON-LD 작성자 일치) 체크**를 `schemaContentMatch`와 함께 둔다.

**권장 author 완성형 (샘플):**

```json
"author": {
  "@type": "Person",
  "name": "김철수",
  "jobTitle": "대표원장",
  "description": "샘플치과 대표원장, ○○대학교 치의학대학원 석사",
  "url": "https://sample-dental.example.com/doctors/kim-chulsoo",
  "sameAs": [
    "https://www.linkedin.com/in/sample-doctor",
    "https://www.youtube.com/@sample-doctor",
    "https://blog.naver.com/sample-doctor"
  ],
  "worksFor": { "@type": "Dentist", "name": "샘플치과", "url": "https://sample-dental.example.com" },
  "alumniOf": "○○대학교 치의학대학원"
}
```

### 4.5 문의 접수함 (Inquiries) ★ — 최우선 모듈

> **전문직/로컬 비즈니스는 문의 응답 속도가 곧 매출.** 사이드바에 미답변 뱃지를 상시 노출한다.

| 필드 | 설명 |
|------|------|
| 접수 내용 | 이름·연락처·서비스 유형·문의 |
| 상태 | 신규 / 처리중 / 완료 (탭 + 원클릭 전환) |
| 접수일시 | 정렬 |
| 메모 | 내부 응대 기록 |

- **비회원도 접수 가능:** 공개 폼의 등록(insert)만 익명 허용, **조회·수정은 관리자 전용** (스팸·개인정보 보호의 핵심 경계)
- **개인정보 보호:** 목록에선 연락처 **마스킹**, 상세에서만 전체 표시. 보관기간 정책 명시
- 알림: 신규 문의 시 관리자 알림 — 이메일/알림톡은 후순위, **우선 대시보드·사이드바 뱃지**로
- (예약 업종이면) **예약 관리** 추가: `이름·연락처·서비스·희망일시·상태(요청/확정/취소/노쇼)·메모`. 캘린더 UI는 과투자 — **날짜별 목록**으로 시작

> **★ 참고 구현 있음** → [04_supabase_참고구현/schema.sql](04_supabase_참고구현/schema.sql)의 `inquiries` 테이블 + RLS(`anon insert` / `admin read`). 허니팟은 프론트 폼 + 서버 라우트에서 검사.

## 5. 🖼️ 미디어
이미지·파일 업로드 라이브러리 + **alt 텍스트 관리** (접근성·이미지 SEO).

- **저장소 확정 = Cloudflare R2** ([06 세팅가이드](06_인증_저장소_세팅가이드.md) CP-4). 관리자 서버 라우트에서 S3 SDK로 R2 업로드(기본), 대용량·영상은 presigned URL 직행 업로드. `media` 테이블엔 공개 URL·**alt·width·height**를 저장.
- ⚠️ **alt는 업로드 폼의 필수값으로 강제한다.** 비워둔 채 저장되면 이미지 SEO·접근성이 동시에 죽고, 나중에 일괄로 채우는 일은 실제로 일어나지 않는다. `saveBlogWithJsonLd()`도 대표 이미지의 alt가 공백이면 저장을 거부한다.
- ⚠️ **width·height도 업로드 시 실측 저장.** `og:image:width/height`와 schema.org `ImageObject`가 이 값을 쓴다. (Google Article 가이드: 최소 50K픽셀 = w×h, 16:9 권장)
- 영상 등 대용량은 **presigned URL로 브라우저 → R2 직행 업로드** (서버 body 제한 회피).
- OG 이미지·JSON-LD `logo`/`image`가 참조하는 공개 URL은 **커스텀 도메인으로 안정화** — 봇이 읽는 주소가 바뀌면 GEO 신호가 깨진다.

### 6.4 로그·시스템 (운영 안전망) ★

> 확정 스택 연결: **백업 대상 = Supabase Postgres**, **백업 저장소 = Cloudflare R2** ([06 세팅가이드](06_인증_저장소_세팅가이드.md) CP-4의 자격증명 재사용). Supabase 자체 백업이 있으나, R2 논리 덤프를 병행하면 스택 독립성·복원 가이드를 스스로 통제할 수 있다.

| 기능 | 설명 |
|------|------|
| **DB 백업** | 일별 크론 + 수동 버튼 → 전 컬렉션/테이블을 gzip 덤프해 **R2 `backups/db/<시각>/` 경로**에 보관 + 복원 가이드(RESTORE.md) 동봉 + 이력·다운로드 링크. **새 컬렉션이 생기면 백업 목록(BACKUP_TABLES)에 반드시 추가** |
| **DB 헬스** | 저장 용량·사용량 게이지(예: Supabase 무료 티어 DB 500MB·MAU 50K 한도), 테이블별 크기 — 관리자 전용 RPC/API로만 조회 |
| **감사 로그 (선택)** | 관리자 쓰기 액션을 `audit_logs(누가·무엇을·언제)`에 기록 |

- ⚠️ **백업 파일엔 문의자 연락처 등 개인정보가 포함된다.** 백업 경로는 공개 서빙 도메인에 연결하지 말 것(미디어와 버킷을 분리하거나 `backups/` 경로를 비공개 유지). 다운로드는 관리자 확인 후 **단기 서명 URL**로만.

**CP-0 유형별 백업 변형 (06 §0 라우팅과 세트):**

| 유형 | 백업 대상 | 기본 설계 대비 변경점 |
|------|-----------|----------------------|
| **① 로그인 없는 자사 홈페이지** | Supabase Postgres **1개** | 기본 설계 그대로. 백업 크론은 자동 발행 스케줄러(7.2)와 **같은 Railway 상주 서버**에서 실행(또는 Supabase 예약 함수). 미디어 파일은 R2가 원본(DB엔 메타만)이라 DB 백업 대상 아님 |
| **② 회원 기능** (방문자 소셜 로그인) | Supabase Postgres **1개** — 회원 계정 포함 | DB가 하나이므로 백업 잡도 1개(콘텐츠·문의·회원 한 번에). **Supabase Free 플랜은 자동 백업이 없으므로 자체 크론 덤프 필수.** 회원 계정은 개인정보 민감도 최상 → 암호화 보관 권장 |
| **③ Supabase 풀스택** (강의·자사몰) | Supabase Postgres 1개 — **주문·결제 원장 포함** | **백업 주기는 그대로 일별.** 실시간 백업(PITR)은 필수 아님 — 대신 ⑴ **결제 웹훅·주문 이벤트를 발생 즉시 기록**(PG 거래ID를 주문에 저장 + 웹훅 로그 보관) → DB가 백업 시점 이후에 죽어도 **PG사 원장으로 그날 주문을 재구성(대사)** 가능 ⑵ 감사 로그(위 표)를 선택 → **필수**로 격상 ⑶ 주문·결제 기록은 **법정 보존기간(전자상거래법상 계약·결제 기록 5년)** 을 백업 보관주기에 반영 ⑷ PITR(시점 복구)은 "하루치 주문 유실을 대사로도 감당 못 하는 규모"가 됐을 때 승격하는 **성장 옵션** |

> **구버전 대비:** 예전엔 유형별로 Payload(Railway) / 하이브리드(DB 2개)로 갈렸으나, 이제 **세 유형 모두 Supabase Postgres 1개**라 백업 구조가 단순해졌다(DB 2개 관리 불필요).

> 공통 뼈대는 동일: R2 `backups/` 비공개 경로 + 일별 크론 + 수동 버튼 + RESTORE.md + 이력. 유형이 바뀌면(②→③ 확장 등) 이 표의 해당 행 기준으로 백업 설계를 승격한다.

### 7.1 `geo` 모드 결과의 blogs 저장 방식 ★확정 (2026-07-22, Supabase 매핑)

**완성형 HTML(`html`)을 본문에 그대로 저장하지 않는다.** 05가 HTML 렌더 전에 만드는 **구조화 JSON(GeoArticle)** 을 blogs 컬럼에 매핑해 저장한다. 저장은 반드시 [saveBlogWithJsonLd()](04_supabase_참고구현/lib/saveBlogWithJsonLd.ts) 단일 함수를 거친다 (JSON-LD 자동 조립):

| GeoArticle 필드 | Supabase blogs 컬럼 |
|-----------------|--------------------|
| `title` / `slug` / `category` | `title` / `slug` / `category_id`(FK) |
| `keyAnswer` + `tldr` 요지 | `excerpt` (meta description·AI 인용 요약) |
| `lede` · `keyAnswer` · `tldr` · `quoteReady` | `lede`·`key_answer` 컬럼 + `tldr`·`quote_ready` JSONB — 프론트가 박스형 렌더 |
| `sections` (heading+html) | `sections_html` JSONB([{heading, html}]) — 자동발행 본문. 수동 글은 `content` JSONB |
| `faq` | `faqs` JSONB → JSON-LD FAQPage 자동 조립 (buildJsonLd) |
| `glossary` | **glossary 테이블에 누적** — 글마다 사전이 자동으로 자람 |

05의 `renderGeoArticleHtml`(목차·인용박스 디자인 CSS)은 **admin 저장용이 아니라 프론트 렌더러 컴포넌트의 참고 디자인**으로 사용한다.

**근거 (실측 admin 스크린샷으로 확인):** 성과 검증된 실제 운영 admin도 ① 본문 = richText(H2 위계) ② JSON-LD = 별도 필드 ③ 디자인 = 프론트 담당 구조였다. HTML 덩어리 저장은 사이트 리디자인 시 전 글 재발행 필요 + 운영자가 admin에서 수정 불가 + "미리보기 = 실제 렌더러"(운영 원칙 2) 위배.

### 7.2 자동 발행 스케줄러 ★ (실제 구축자 확인 사항 — Railway 상주 작업)

> **핵심 요구:** 네이버 블로그에 글이 올라오면 자동으로 각색해서 홈페이지에 포스팅. **매일 5~6개, 개수는 관리자 페이지에서 세팅 가능.**

**동작 흐름 (Railway에서 상시 실행):**

```
[주기 폴링: 연동된 네이버 블로그 새 글 감지]   ← 05의 fetchPostList (예: 1시간 간격)
        ↓ 미처리 원글을 발행 큐에 적재 (blogId+logNo로 중복 방지)
[일일 발행 한도 확인: 오늘 N개 미만인가?]      ← N = 관리자 설정값 (기본 5~6)
        ↓ 한도 내에서
[geo 모드 각색 (05) → 구조화 JSON → Blogs 저장 (7.1 매핑)]
        ↓ 발행 모드에 따라
[자동 모드: 즉시 status=발행  /  검수 모드: status=초안 → 관리자 승인 대기]
```

**관리자 설정 필드 (GEO 엔진 → 자동 발행 설정):**

| 필드 | 설명 |
|------|------|
| 연동 네이버 블로그 | blogId (복수 가능) |
| **일일 발행 개수** | 기본 5~6. 관리자가 조정 |
| 발행 모드 | **자동**(각색 즉시 발행) / **검수**(초안 대기 → 승인 후 발행) |
| 발행 시각 분산 | 하루에 몰아서가 아니라 시간대에 분산 발행 (자연스러운 발행 패턴) |
| 실행 이력 | 마지막 폴링·발행 시각, 성공/실패 로그 (6.4 연동, 대시보드 "발행 현황" 위젯에 표시) |

- 운영 권장: **초기엔 검수 모드로 시작** → 각색 품질 안정 확인 후 자동 모드 전환. 자동 모드에서도 원글이 본인 소유 블로그 글이므로 사실관계 리스크는 낮지만, `schemaContentMatch` 계열 가드(없는 서비스 키워드 유입 여부)는 주기 점검한다.
- ⚠️ **SSR 최종 확인 (구축자 강조):** 자동 발행이 돌기 시작하기 전에, robots/llms/JSON-LD가 **프론트(Vercel)에서 SSR로 출력되는지 반드시 실측** — 발행 글 1편을 `curl`로 받아 첫 응답 HTML `<head>`에 JSON-LD가 있는지 확인 (8장 커버리지표의 1순위 항목).

## 8. 🧩 Supabase 참고 구현 (요지)

> 실제 코드는 [04_supabase_참고구현/](04_supabase_참고구현/) 폴더. 실측 admin 구조를 스키마·RLS·저장함수로 재현 + GEO 자동화.

```
04_supabase_참고구현/
├── schema.sql              ← 테이블 9(blogs·keyword_pages·staff·…) + settings 3 + RLS 정책
├── lib/
│   ├── supabase.ts         ← anon(읽기)·service_role(쓰기) 클라이언트
│   ├── buildJsonLd.ts      ← JSON-LD @graph 조립 순수함수 (buildAuthor·Business·FAQPage)
│   ├── saveBlogWithJsonLd.ts ← ★GEO 심장부 (저장 단일 진입점 = Payload 훅 대체)
│   └── scheduler.ts        ← 네이버 자동발행 (Railway 상주, service_role write)
└── 학습가이드_Supabase판.md
```

**saveBlogWithJsonLd() 동작 (저장 시 반드시 이 함수 경유 — 자동 훅 대체):**
1. `settings_business`에서 전역 비즈니스 정보를 읽음 (Payload findGlobal 대체)
2. `staff`에서 author를 조회해 **4.2 완성형 Person**(name·jobTitle·description·url·**sameAs**·alumniOf·worksFor) 조립
3. `@graph` = [ BlogPosting, [업종]Business(전역 주입: 주소·좌표·전화·영업시간), FAQPage(글의 faqs 변환) ] 조립
4. `structured_data` 컬럼에 담아 blogs에 insert
   → **저장하는 모든 경로가 이 함수만 호출**하므로 JSON-LD 누락 불가 (Payload 자동 훅과 동등 효과)

**blogs 구현 포인트:**
- `structured_data`는 `jsonb` — saveBlogWithJsonLd가 채움 (직접 insert 금지)
- `slug`는 unique + 인덱스, 저장 전 슬러그화 (ASCII-safe)
- `sections_html`/`content`는 JSONB — H2 위계 구조 보존
- **RLS**: read는 `status='published'`만 공개(anon), write는 service_role/관리자(is_admin) — Payload access 대체
- 리스크 가드 2종 컬럼: `schema_content_match` + `author_identity_match`
- SEO: `seo_title`/`seo_description` 컬럼 + 프론트에서 글자수 검사 UI 직접 구현 (Payload plugin-seo 대체)

## 부록 A. 반복 구현 패턴 (스택 중립)

> Supabase(RLS) 스택 기준 원문 코드는 `admin-page-playbook-universal.md` §5 참조. 여기서는 스택 무관 원칙만.

- **권한 2중 방어:** 페이지 가드(`requireAdmin`) = UX용 1차 / 데이터 계층(**Supabase RLS + `is_admin()`**) = 진짜 방어. 접수(문의·예약) 데이터는 **"익명 등록 허용(anon insert) + 조회는 관리자만(admin read)"** 패턴.
- **AI 초안 생성 (JSON mode):** 낮은 temperature(≈0.4) + JSON 강제 출력 + **"빈 칸만 채우기"**(운영자가 이미 쓴 내용은 보존) + 완료 시 "✓ AI 초안 채움 — 검토 후 저장하세요" 안내. 시스템 프롬프트에 업종 페르소나 + 법적 금지표현(효과 보장·최상급 금지) 포함.
- **이미지 업로드:** 붙여넣기(clipboardData의 files **와 items 둘 다** 처리 — 스크린샷은 items로만 옴)·드래그·파일선택 → 스토리지 `{모듈}/{엔티티id}/{uuid}.{ext}` → 본문 삽입. 서버 액션 body 기본 1MB 제한 상향 주의.
- **드래그앤드롭 정렬:** 화면에서 배열 재배치 → 전체 id 배열을 서버에 전달 → 서버가 소유 검증(id 집합 일치) 후 sortOrder 일괄 update.
- **성능 체크:** ① **서버 함수 리전 = DB 리전(서울)** 부터 — 미국↔서울 왕복이면 페이지당 2초+ ② N+1 금지(조인 1왕복) ③ 페이지 진입 쿼리 `Promise.all` ④ 로딩 스켈레톤 + 저장 버튼 pending.
- **배포 전 검증:** 타입체크·테스트 + **관리자/일반회원/비로그인 3역할 E2E**(특히 문의 내역 등 개인정보 접근 경계) + 테스트 데이터는 반드시 정리(라이브 노출 사고 방지) + 배포 후 프로덕션 실측.

## 부록 B. 커스텀 프로토콜 — 기존 사이트에 맞춤 관리자 도출

> 이 설계서를 그대로 찍어내지 말고, 대상 사이트가 **실제로 가진 기능**을 스캔해 "이 사이트만의 관리자"를 도출할 때 사용.

**① 인벤토리 수집:** DB 마이그레이션/컬렉션(데이터 구조의 진실) · 공개 라우트(방문자 화면 목록) · 쓰기 경로(서버 액션·API·공개 폼) · 외부 연동(env 키) · 자동화(cron·웹훅)를 스캔.

**② 도출 규칙 (발견 → 관리자 니즈, 기계적 매핑):**

| 사이트에서 발견되면 | 관리자에 반드시 필요 | 우선순위 |
|---|---|:---:|
| 비회원이 등록하는 데이터(문의·신청·댓글) | 목록+상태 관리+미처리 뱃지, 개인정보 마스킹 | ★★★ |
| `status`/`isPublished` 플래그 있는 콘텐츠 | 초안↔공개 CRUD + 실제 화면 미리보기 | ★★★ |
| 돈이 움직이는 데이터(주문·구독·포인트) | 원장 조회 + 취소/환불(트랜잭션) + KPI | ★★★ |
| 사용자 생성 콘텐츠(후기·댓글) | 모더레이션(숨김/삭제/신고 처리) | ★★ |
| 파일 업로드 경로 | 업로드 현황·용량, 고아 파일 정리 | ★★ |
| 외부 API 연동(PG·메일·LLM) | 호출 로그·실패 알림·비용 모니터링 | ★★ |
| cron/웹훅 | 실행 이력 + 마지막 성공 시각 | ★★ |
| 예약·일정 데이터 | 날짜별 목록 + 상태 전환 | ★★ |
| 하드코딩된 정적 서브페이지 다수 | 2.6 페이지 관리로 이관 | ★★ |
| 어떤 데이터든 존재 자체 | DB 백업 목록 포함 + 헬스 노출 (6.4) | ★★★ |

**③ 산출물 — 관리자 커버리지 매트릭스:**

```
| 사이트 기능(발견) | 근거(컬렉션/라우트) | 필요한 관리자 기능 | 이 설계서 매핑 | 상태 |
|---|---|---|---|---|
| 상담 신청 폼 | inquiries, /apply | 목록+상태+뱃지 | 4.5 문의 접수함 | ❌ 없음 → 신규 |
```
상태: ✅ 있음 / ⚠️ 부분 / ❌ 없음. **매핑 없음 = 커스텀 모듈** — 부록 A 패턴을 조합해 새로 설계하되, 스펙은 "운영자가 이 기능으로 매일 무엇을 결정하는가?"에서 출발.

**④ 실행:** ❌·⚠️를 우선순위순 정렬 → 범위 합의 → 모듈별 구현(데이터 모델→백업 등록→액션→화면→메뉴→3역할 검증) → 매트릭스 갱신·보관.
