# 사이트 디자인 해체 프롬프트 (Design Deconstruction → Build Prompt)

아래 프롬프트에 URL만 넣어서 사용하세요. 사이트를 열람/분석할 수 있는 환경(Claude Code, 브라우저 DevTools 덤프 첨부 등)에서 가장 정확하게 동작합니다.

> ⚠️ **먼저 읽어라 — [벤치마킹-실전-해부가이드.md](벤치마킹-실전-해부가이드.md):** 이 문서는 "무엇을 해체할지"를 정한다. 하지만 **WebFetch 요약만 믿고 재현하면 반드시 틀린다**(실증: 색·섹션·인터랙션 오인). 실제 HTML/CSS/JS를 받아 읽는 법, 슬라이더·스크롤리빌 같은 인터랙션의 정체를 소스에서 확정하는 법, Playwright로 재현물을 실측 검증하는 법은 그 가이드에 있다. **해체 착수 전 그 가이드의 STEP A~E를 먼저 실행**하라.

---

당신은 디자인 리버스 엔지니어링 전문가다. 아래 사이트를 해체 분석해서, **다른 AI에게 그대로 건네면 이 사이트를 1:1로 재현할 수 있는 "Build Prompt"**를 작성하라.

분석 대상: {사이트 URL}

## 절대 규칙

1. **형용사 금지, 측정값만.** "세련된", "모던한", "부드러운" 같은 표현을 쓰지 마라. 대신 정확한 hex 컬러, px/rem 값, 클래스명, duration(ms), easing 함수, delay 값을 써라.
2. **CSS는 원문 그대로.** 디자인 시스템의 핵심 유틸리티(글래스모피즘, 그라디언트 보더, 커스텀 섀도 등)는 요약하지 말고 실제 CSS 코드 블록으로 verbatim 기술하라.
3. **텍스트 카피는 실제 문구 그대로 인용하라.** "적절한 헤드라인" 같은 플레이스홀더 금지.
4. **에셋은 실제 URL로.** 이미지/비디오/폰트의 실제 src를 나열하라. 접근 불가하면 해상도·비율·내용 설명으로 대체하고 `[에셋 설명]`으로 표시하라.
5. **애니메이션은 숫자로 명세하라.** initial 상태 → animate 상태, duration, delay, easing, stagger 간격, 트리거 조건(스크롤 진입 %, hover, load)까지.
6. **확인하지 못한 값은 지어내지 말고 `[추정]` 태그를 붙여라.** 확인한 값과 추정한 값이 섞이면 재현 프롬프트로서 가치가 없다.
7. **동작 로직은 의사코드 수준까지.** 커스텀 JS 동작(크로스페이드, 캐러셀, 패럴랙스, 인터섹션 옵저버)은 상수·이벤트·분기 조건을 명시하라. (예: `FADE_MS = 500`, `timeupdate에서 duration - currentTime <= 0.55이면 fadeTo(0)`)
8. **클릭 가능한 모든 요소는 목적지까지 기록하라 (링크 맵).** 배너·카드·썸네일·CTA·내비 항목마다 실제 href 목적지(어느 페이지/앵커/외부 URL인지)를 명시하라. 재현 시 `href="#"` 플레이스홀더로 남기는 것을 금지한다 — 목적지 페이지가 아직 없으면 어떤 페이지로 연결되어야 하는지 의도를 적어라. (예: "메인 프로모션 그리드 8개 썸네일 → 이벤트 목록 페이지", "온라인상담 카드 → 하단 고정 예약폼 포커스") 페이지들이 유기적으로 연결되지 않은 사이트는 미완성이다.
9. **지식성 콘텐츠(도메인 사실)는 지어내지 말고 웹검색으로 교차검증 후 작성하라.** 시술 정보(시술시간·마취·유지기간·권장주기), 제품 스펙, 가격 구조, 법적 고지 같은 사실 기반 콘텐츠는 디자인과 달리 원본을 복사할 수도, 임의로 채울 수도 없다 — 페이지마다 같은 값을 복붙하는 것은 최악이다. 재현 시 항목별로 웹검색을 돌려 **최소 3개 소스에서 교차 확인된 값만 사용**하고, 페이지(시술/제품)마다 값이 서로 달라야 정상임을 인지하라. (예: 울쎄라 유지 약 12개월·연 1회 / 슈링크 3~4개월 간격 / 보톡스 3~6개월 / 레이저토닝 1~2주 간격 10회+ — 전부 다르다) 검증이 안 되는 값은 그럴듯하게 채우지 말고 `[미검증]`으로 표시하라.
10. **FAQ는 내가 지어낸 질문이 아니라 실제 연관검색어 기반으로 작성하라.** 페이지 주제마다 웹검색으로 사용자들이 실제로 검색하는 질문(연관검색어·자동완성·커뮤니티 Q&A)을 수집한 후 FAQ를 구성하라. 사용자가 진짜 궁금해하는 것은 불안·비교·회복 질문이다. (실측 예: "인모드 볼꺼짐", "눈밑필러 실명", "필러 녹이기", "리쥬란 통증", "보톡스 음주", "토닝 색소침착 리바운드", "울쎄라 병원마다 가격 차이") 답변 역시 규칙 9의 교차검증을 거친 사실로만 작성한다 — 이 FAQ가 곧 FAQPage 스키마가 되어 AI 검색 인용의 핵심 소스가 된다.
11. **★ 벤치마킹 원본의 상호명·신상은 절대 결과물에 넣지 마라.** 규칙 3(카피 원문 인용)의 유일한 예외다 — 원본 업체의 상호명(한글·영문 표기 모두), 원장/직원 실명, 전화번호, 주소, 사업자번호, 도메인, SNS 계정은 해체 문서에 기록할 때부터 `{상호명}`, `{대표전화}` 같은 플레이스홀더로 치환하라. 문장 구조와 어투는 그대로 두고 신상만 바꾼다. (예: 원본 "새론의원이 알려드립니다" → "{상호명}이 알려드립니다") 남의 상호가 내 사이트에 박히는 것은 디자인 오류가 아니라 **법적 사고**다. 상호명이 이미지 안에 박힌 에셋(로고, 워터마크 있는 사진)은 재사용 금지로 표시하고 대체 에셋 필요로 기록하라.

## 분석 절차

1. HTML 소스와 로드되는 CSS/JS/폰트/미디어 리소스를 실제로 확인하라 (가능하면 fetch, 불가하면 제공된 스크린샷/덤프 기반).
2. 사용 기술 스택 식별: 프레임워크(React/Vue/바닐라), CSS 방식(Tailwind/CSS-in-JS/커스텀), 애니메이션 라이브러리(Framer Motion/GSAP/CSS), CDN 여부와 **정확한 버전**.
3. 디자인 토큰 추출: 배경/텍스트/액센트 컬러(hex/rgba), 폰트 패밀리와 weight, border-radius 규칙, 그림자, 간격 스케일.
4. 반복되는 UI 패턴을 "디자인 시스템 유틸리티"로 묶어라 (예: 글래스 카드, pill 버튼, 태그 칩).
5. 페이지를 섹션 단위로 위에서 아래로 해체하라.

## 출력 형식 (이 구조를 그대로 따를 것)

### `Build Prompt: {사이트 성격을 요약한 제목}`

**개요 (1문단):** 페이지 구성(섹션 수, 각 섹션 역할), 배경 처리 방식, 공유 디자인 시스템, 애니메이션 방식을 한 문단으로.

**Tech stack (pinned):** 실제 사용 라이브러리와 버전. CDN이면 `<script>` 태그 원문 그대로. 마운트 방식(#root, SSR 등)과 body 기본 배경색.

**Fonts:** Google Fonts 등 로드 쿼리스트링 원문, 각 폰트의 용도 매핑(heading/body), weight 목록, italic 사용 여부, Tailwind config 확장이 있다면 그 내용.

**Design Tokens & 공통 유틸리티:** 핵심 재사용 CSS를 클래스별로 코드 블록에 원문 기술. 변형(subtle/strong 등)이 있으면 차이점만 주석으로.

**커스텀 컴포넌트 명세:** 재사용 컴포넌트마다 — 이름, props/상태, 상수 값, 이벤트 핸들러별 동작, 클린업 로직, 일반 구현과 다른 점(예: "loop 속성 OFF, ended 이벤트로 수동 루프").

**섹션별 해체 (위→아래 순서):** 각 섹션마다
- 컨테이너: 높이(min-h-screen 등), 배경(색/이미지/비디오 + 실제 URL + object-fit/position + 스케일), 오버레이 유무, z-index 레이어링
- 각 자식 요소를 DOM 순서대로: 정확한 클래스(Tailwind면 클래스 문자열 그대로), 인라인 스타일, **실제 텍스트 카피**, 아이콘, 크기
- 요소별 진입 애니메이션: initial → animate 값, duration, delay, easing, 트리거
- 반응형 분기: 브레이크포인트별로 달라지는 것만 명시

**아이콘:** 커스텀/인라인 SVG는 path 데이터 원문 그대로. 아이콘 라이브러리면 라이브러리명 + 아이콘명 + 크기/stroke 설정.

**Notes:** 재현 시 빠뜨리기 쉬운 디테일 — 자간 때문에 nbsp 대신 margin을 쓴다든가, CSS transition 대신 rAF를 쓰는 이유, 콘솔 경고 처리, 특정 브라우저 prefix 등.

**마지막 줄:** "위 프롬프트는 이 페이지의 모든 요소, 스타일, 애니메이션, 에셋, 폰트를 담고 있어 그대로 재현할 수 있다"는 확인 문장과 함께, `[추정]` 표시된 항목이 있다면 그 목록을 요약하라.

## 멀티 페이지(사이트 전체) 모드

메인 페이지만이 아니라 사이트 전체를 벤치마킹할 때는, 위 프롬프트 앞에 아래 지시를 붙인다.
핵심 원칙: **"모든 페이지를 해체"가 아니라 "모든 템플릿을 해체"** — 페이지는 수십 개라도 템플릿은 보통 3~5개다.

> 이 사이트 전체를 벤치마킹하라. 단, 페이지 단위가 아니라 **템플릿 단위**로 작업한다.
>
> **Phase 1 — 사이트맵 수집:** GNB/푸터/사이트맵에서 전체 페이지 URL 트리를 추출하라. (뎁스 구조 그대로: 센터 > 시술 상세)
>
> **Phase 2 — 템플릿 분류:** 페이지들을 서로 다른 레이아웃 템플릿으로 분류하라. (예: 메인 / 시술 상세 / 이벤트 목록 / 이벤트 상세 / 오시는길 / 의료진 소개) 각 템플릿에 속하는 페이지 수를 명시하라. 판단 기준은 URL 패턴이 아니라 **실제 마크업 구조**다 — 최소 유형별 2개 페이지를 열어 구조가 같은지 확인하라.
>
> **Phase 3 — 템플릿별 해체:** 유형별 대표 페이지 1개씩만 골라 위의 해체 규칙대로 Build Prompt를 작성하라. 헤더/푸터/퀵메뉴/고정폼 같은 **공통 셸은 한 번만 기술**하고, 각 템플릿에서는 셸 아래 본문 구조만 기술하라. 본문이 통이미지(긴 JPG 스택)로만 구성된 템플릿이면 CSS 해체 대신 **"콘텐츠 슬롯" 정의**로 대체하라: 슬롯 순서, 각 이미지의 역할(도입부/시술설명/전후사진/가격표), 폭·비율, PC/모바일 스왑 여부. **콘텐츠 밀도도 원본과 맞춰라** — 원본 상세 페이지의 콘텐츠 블록 수를 세고(예: 통이미지 6블록 = 도입·원리·모드소개·추천대상·과정·FAQ 분량), 재현 시 같은 수준의 섹션(원리 설명 / 추천 대상 / 시술 과정 / FAQ 등)을 채워라. 셸만 재현하고 본문을 도입 한 문단으로 끝내면 디자인은 같아도 콘텐츠 퀄리티에서 원본과 확연히 차이 난다.
>
> **★ Phase 3.5 — 통이미지 본문은 반드시 "받아서 눈으로" 콘텐츠 실측 (필수·건너뛰기 금지):** 상세 본문이 통이미지(JPG/PNG 스택)면 **텍스트가 이미지 안에 있어 grep·DOM 파싱으로는 절대 안 잡힌다.** 이미지 개수·before/after 슬라이드 수만 세고 넘어가면 **"셸만 재현하고 본문은 도입 한 문단"인 부실 상세**가 나온다(실측 실패 사례: 2026-07 린 피부과 1차 상세 — 기법·지표·강조배너 다 누락). 반드시 아래를 실행한다:
> 1. 대표 상세페이지의 **본문 통이미지를 curl로 실제 다운로드**한다 (`/_files/…jpg` 등, 큰 용량 = 본문 콘텐츠일 확률 높음).
> 2. 받은 이미지를 **Read로 하나하나 눈으로 열어** 그 안의 실제 카피·섹션 구성을 읽는다. (예: "○○는 {상호명}" 강조문 / **시술 기법 N종**(스프레딩·레이어드 등 일러스트+라벨) / **지표 게이지**(통증·개선도·지속력) / "절개없이" 강조배너 / 전후 안내문 등)
> 3. 읽어낸 **실제 섹션을 콘텐츠 슬롯 목록으로 전수 기록**하고, 재현 시 그 섹션들을 상호만 치환해 그대로 재현한다. 원본에 기법 2종·지표 바가 있으면 내 상세에도 있어야 한다.
> 4. ⚠️ 통이미지 안의 **원본 상호·워터마크·원장실명·환자 실사진**은 재사용 금지 → 자사 에셋으로 대체(전후사진은 AI 생성 금지, 규칙 11 + 에셋 안전원칙). 대신 기법 일러스트·개념컷은 자사 톤으로 재생성.
> **한 줄 규칙: 상세 본문이 통이미지면 "몇 장인지" 세지 말고 "무슨 내용인지" 받아서 읽어라.**
>
> **Phase 4 — 콘텐츠 매트릭스:** 해체하지 않은 나머지 페이지는 표로 정리하라: URL / 템플릿 유형 / 페이지 제목 / 본문 자산 목록(이미지 URL, 인터랙티브 위젯 유무). 재현 시 이 표의 각 행이 "템플릿 + 콘텐츠"로 생성된다.
>
> **Phase 5 — 링크 맵 (유기적 연결 검증):** 각 페이지의 클릭 가능 요소(내비, 배너, 카드, 썸네일, CTA, 퀵메뉴)가 어디로 연결되는지 출발지 → 목적지 표로 정리하라. 특히 메인 페이지의 각 섹션(프로모션 그리드 → 이벤트 목록, 시술 카드 → 시술 상세, 상담 CTA → 예약폼)이 어느 서브페이지와 연결되는지 빠짐없이 기록하라. 재현 완료 기준: **모든 페이지에서 `href="#"` 데드링크 0건** — 목적지가 없는 요소는 만들지 말거나 만든 페이지로 연결하라.

**왜 이렇게 하나:** 한국형 웹빌더 병원/쇼핑몰 사이트의 서브페이지는 대부분 (공통 셸) + (통이미지 본문) + (간헐적 위젯: 전후사진 슬라이더, 탭, 지도) 구조다. 실측 예: beautynyoung의 시술 상세 페이지는 본문이 이미지 스택 + before/after 스와이퍼(28슬라이드)로, 해체할 고유 CSS가 거의 없다. 이런 페이지를 전부 개별 해체하면 토큰만 낭비되고, 재현에 필요한 정보(어떤 콘텐츠 이미지를 만들어야 하는가)는 오히려 빠진다.

> **★ 재현 밀도는 원본을 넘어선다 → [세부페이지-콘텐츠-밀도-규칙.md](세부페이지-콘텐츠-밀도-규칙.md) 필독.** Phase 3.5로 원본 콘텐츠를 실측·재현하되, 거기서 멈추지 말고 **각 서비스 상세에 원리(문단)/과정(단계)/비교(2열)/제품·장비 라인업(각 설명)**을 규칙 9(3소스 교차검증) 기반으로 채운다. "이름 나열"이 아니라 "각 항목을 문단으로 설명"하는 것이 정교한 상세와 얇은 상세를 가른다. 이 밀도는 병원·법률·기타 업종 불문 공통이다.

## SEO / GEO 재현 체크리스트

재현(구현) 단계에서는 디자인·콘텐츠와 함께 아래 세팅을 기본 포함하라. 원본 사이트에 없더라도 넣는다 — 벤치마킹의 목적은 원본보다 잘 만드는 것이다.

**SEO (검색엔진):**
- `<title>`에 **지역+핵심 키워드** 포함 (예: "강남 눈밑지방재배치 필러 | ○○의원") — 페이지마다 다르게
- 페이지별 `meta description`(고유 문장) / `keywords` / `robots` / **`canonical`**
- Open Graph(og:title/description/image/url/locale) + Twitter Card — og:image는 해당 페이지 대표 이미지
- 다국어 페이지가 있으면 `hreflang` 상호 연결 + `x-default`, 언어판별 canonical과 `og:locale` 분리
- `sitemap.xml`(전 페이지, 우선순위·changefreq) + `robots.txt`
- 이미지 `alt`는 파일명이 아니라 실제 내용 설명으로 — **키워드 + 상황을 문장으로** (나쁨: `alt="img_001.jpg"` / 좋음: `alt="공장 내부 무대에서 진행되는 준공식 기념 순서"`). 단 **순수 장식 이미지는 `alt=""`가 정답**(스크린리더가 건너뜀). 콘텐츠 이미지와 장식 이미지를 구분해서 처리하라.
- **모든 발행 콘텐츠에 대표 이미지(og:image)** — `og:image`는 절대 URL + `og:image:width/height/alt` 동반. 최소 50K픽셀(w×h), 16:9 권장(Google Article 가이드). 대표 이미지가 없으면 SNS 공유 카드·검색 썸네일이 전부 빈다
- **검색엔진 소유확인 메타** — 구글 서치콘솔 + **네이버 서치어드바이저**(`<meta name="naver-site-verification">`). 국내 사이트는 네이버가 별도 축이며 구글 등록으로 대체되지 않는다

**GEO (AI 검색 인용 최적화):**
- **JSON-LD 구조화 데이터**를 페이지 성격에 맞게: LocalBusiness/MedicalClinic(상호·주소·전화·영업시간), 상세 페이지엔 Product/MedicalProcedure(+howPerformed), **FAQPage**(규칙 10의 실검색어 FAQ 그대로), BreadcrumbList
- FAQPage 스키마와 화면의 FAQ DOM은 **반드시 동일 내용으로 동기화** (생성 스크립트에서 한 소스로 뽑을 것)
- robots.txt에 AI 크롤러 명시 허용: GPTBot, ClaudeBot, PerplexityBot, Google-Extended
- 사실 문장은 수치와 함께 명확하게 (AI가 인용하기 좋은 형태: "울쎄라는 약 12개월 유지되어 연 1회 시술을 권장합니다")
- 도메인 미정이면 BASE URL 상수로 분리해 배포 시 한 줄 교체 가능하게

## 가독성 & 모바일 체크리스트

재현 단계에서 디자인 값 복제와 별개로 아래를 기본 적용하라. 원본이 지키지 않았더라도 지킨다.

**본문 가독성 (텍스트 배치):**
- 본문 문단의 **행길이를 65~75ch로 제한** (`max-width:68ch` 등) — 와이드 레이아웃에서 문단이 화면 전체 폭으로 퍼지면 읽을 수 없다. 중앙정렬 섹션의 문단은 `margin:auto`로 함께 중앙 배치
- 본문 행간 **170~185%** (한글은 영문보다 행간을 더 준다), 제목 행간 120~135%
- 디스플레이용 음수 자간(-0.03em 이하)을 **본문 문단에 그대로 상속시키지 말 것** — 문단은 -0.01em 수준으로 완화
- 긴 텍스트 블록(FAQ 답변·유의사항·원리 설명)일수록 행길이 제한 + 행간 확대를 우선 적용
- `word-break:keep-all`(한글 어절 단위 줄바꿈) + `img{max-width:100%}` 기본

**모바일 최적화:**
- **절대좌표 요소 전수 점검**: `left:12%`, `left:240px` 같은 데스크톱 좌표는 모바일에서 잘리거나 겹친다 → 모바일에서는 `left:20px; right:20px` 고정 여백으로 전환
- **헤더 충돌 검사**: 로고 + 언어 스위처 + 햄버거가 360px 폭에서 겹치지 않는지 확인 (크기 축소·재배치)
- 이미지 위 텍스트 오버레이(히어로 캡션·배너 문구·서브비주얼 타이틀)는 모바일에서 좌우 여백 확보 + 폰트 스케일 다운
- 풀블리드 비주얼은 모바일에서 높이 재조정 (100vh 히어로는 유지 가능하나 서브비주얼은 50vh 수준으로)
- 다열 그리드의 열 수 축소 규칙 명시 (4열→2열→1열), 카드 패딩·높이도 함께 축소
- 고정 요소(하단 폼·퀵메뉴)끼리 겹침 검사, 터치 타깃 최소 44px
- 검증: 360px·768px 두 폭에서 DevTools로 실제 확인 — 가로 스크롤 발생과 텍스트/버튼 겹침이 0건이어야 통과

## ★ 원본 상호명 유출 검사 (디자인 구현 완료 후 필수 재검)

절대 규칙 11(해체 단계 치환)만으로는 부족하다 — 카피를 옮기다 보면 원본 상호가 반드시 새어 들어온다.
**구현이 끝났다고 판단한 시점에 아래 전수 검사를 한 번 더 돌리고, 0건이어야 완료다.**

**검사 방법 (실패 가능한 체크 — "눈으로 봤는데 없더라"는 검증이 아니다):**

1. 원본 업체의 검색어 목록을 만든다: 상호명 한글 표기, 영문 표기, 축약 표기, 원장 실명, 원본 도메인, 원본 전화번호.
   (예: 새론의원 벤치마킹이면 → `새론`, `saeron`, `thesaeron`, 원장 실명, `thesaeron.kr`)
2. 산출물 **전체 파일**에 대해 각 검색어로 grep 하라. 대상은 화면에 보이는 것만이 아니다:

   | 검사 대상 | 놓치기 쉬운 위치 |
   |---|---|
   | HTML 본문 텍스트 | 푸터 카피라이트, 팝업, 유의사항 문단 속 한 줄 |
   | `<head>` 메타 | title, description, keywords, og:*, twitter:* |
   | **JSON-LD** | name, author, publisher, provider, address — AI가 그대로 인용하는 곳이라 최악의 유출 지점 |
   | 속성값 | 이미지 `alt`, `aria-label`, `title` 속성, placeholder |
   | 파일·경로 | 이미지/에셋 파일명, CSS 클래스명, 주석 |
   | GEO 파일 | robots.txt, llms.txt, sitemap.xml |
   | JS/데이터 | 하드코딩 문자열, 시드/더미 데이터, i18n 문자열 |

3. 이미지도 확인: 원본에서 받아온 에셋 중 로고·워터마크·간판이 찍힌 이미지가 그대로 쓰이지 않았는지 육안 확인.
4. **grep 결과 0건 + 이미지 육안 통과 = 완료.** 1건이라도 나오면 치환 후 1번부터 재검사.

**허용 예외 (잭피부과 구축 실측으로 확정):**
- CMS의 **원글 추적용 관리 필드**(예: 자동 발행의 `sourceUrl`·`sourceLogNo` — 중복 방지에 필수)는 원본 블로그 URL을 담아도 된다. 단 이 경우 **프론트 렌더 HTML에 해당 값이 노출되지 않는지**를 별도로 curl+grep 확인해야 예외로 인정된다 (관리자 API 전용 = OK, 화면·JSON-LD·og에 새면 유출).
- 내부 참고자료 문서(이 폴더의 .md)에 벤치마크 출처를 기록하는 것은 산출물이 아니므로 무방하다.

**실측 사례 (2026-07-13 잭피부과 검사에서 실제로 걸린 것):** 소스 코드 주석에 적어둔 벤치마크 URL이
`public/` 폴더의 CSS 파일에 들어가 있었다 — **주석이라도 공개 서빙되는 파일(css/js)은 브라우저에서
누구나 열람 가능**하므로 유출이다. 출처 기록이 필요하면 내부 문서에 남기고 배포 파일에서는 일반 표현으로 치환하라.

```bash
# 예시: 산출물 루트에서 (검색어는 원본 업체에 맞게 교체)
grep -rniE "새론|saeron|thesaeron" --include="*.html" --include="*.css" --include="*.js" \
  --include="*.json" --include="*.txt" --include="*.xml" --include="*.ts" --include="*.tsx" .
```

> 이 검사는 규칙 9·10의 사실 검증과는 별개다 — 사실은 맞아도 상호가 남의 것이면 사고다.



- **정확도 순서:** 실제 페이지 소스/DevTools 덤프를 함께 주는 것 > AI가 직접 fetch > 스크린샷만 제공. 스크린샷만으로는 CSS 원문·애니메이션 타이밍·에셋 URL을 얻을 수 없어서 `[추정]`이 많아집니다.
- SPA(React 등)는 초기 HTML에 내용이 없을 수 있으므로, 렌더링된 DOM을 복사해 주면(DevTools → Elements → Copy outerHTML) 훨씬 정확해집니다.
- 애니메이션 타이밍이 중요하면 화면 녹화 또는 "히어로 텍스트가 단어별로 0.1초 간격 블러인" 같은 관찰 메모를 덧붙여 주세요.
