# 인증·저장소 세팅 가이드 — 확정 스택 결정사항

> **용도:** 홈페이지 구축 시 AI(바이브코딩)가 이 문서대로 인증·저장소를 세팅하고, **각 단계에 도달할 때마다 사용자에게 필요한 정보를 요청 + 콘솔 가이드를 제공**하기 위한 문서.
> **확정 결정 (사용자 결정, 변경 시 이 문서 갱신):**
> 1. **관리자 = Supabase 기반 커스텀 관리자** (모든 유형 공통 — 관리자 로그인도 Supabase Auth `role=admin`)
> 2. **방문자 로그인 = 구축 시작 시 사용자에게 질문 (CP-0)** — 도입 시에만 카카오/구글 소셜 로그인 추가
> 3. **이미지·영상 저장소 = Cloudflare R2** (Supabase Storage 아님)
>
> **왜 R2인가 (2026-08 요금 기준 · 시작 시 재확인 권장):**
> | | Supabase Storage | Cloudflare R2 |
> |---|---|---|
> | 무료 저장 용량 | 1 GB | **10 GB** |
> | 무료 대역폭(나가는 데이터) | 5 GB | **무제한 — egress $0** |
> | 초과 대역폭 요금 | GB당 $0.09 | **$0** |
> | 초과 저장 요금 | Pro $25/월~ | GB당 월 $0.015 |
>
> - **결정적 이유는 용량이 아니라 대역폭이다.** 이미지·영상은 방문자가 볼 때마다 전송되므로, 트래픽이 늘수록 Supabase는 요금이 비례해 증가한다. R2는 egress가 0원이라 **방문자 수와 요금이 분리**된다.
> - **부차적 이유:** ① 미디어 요청이 DB를 거치지 않아 DB 부하·응답속도에 영향을 주지 않는다. ② 무료 저장 용량이 10배.
> - **구현 형태:** 원본 파일은 R2에 두고, DB `media` 테이블에는 **공개 URL + alt만** 저장한다. 프론트는 `<img src={R2 공개URL}>`로 링크만 참조한다.
>
> ---
> ### 🔄 결정 변경 이력 (Payload → Supabase 단일 전환)
> - **2026-07-12/13 (구버전):** 관리자 = Payload CMS(스택 A), 유형①은 Payload로 라우팅.
> - **2026-07-22 (현행):** 관리자 스택을 **Supabase 단일로 통일**하도록 변경.
>   유형①(로그인 없는 자사 홈페이지)도 Payload 대신 **Supabase 기반 커스텀 관리자**를 쓴다.
>   **이유:** 관리자 UI를 직접 만들 수 있으므로 Payload의 "자동 어드민" 이점이 상쇄되고,
>   스택을 하나로 통일해 유지보수·배포를 단순화. GEO 로직(크롤링·AI변환·JSON-LD 조립)은
>   Payload 무관 순수 로직이라 스택 전환에도 그대로 재사용된다.
>   참고구현은 [04_supabase_참고구현/](04_supabase_참고구현/) 로 교체됨.

## 0. ★ CP-0: 사이트 유형 판별 — 구축 시작 시 반드시 사용자에게 질문 (스택 라우팅)

> **AI 빌더 규칙:** 구축을 시작하기 전에 **"이 홈페이지가 어떤 유형인가"** 를 아래 스크립트로 질문하고, 답에 따라 스택을 안내한다. GEO 홈페이지의 핵심 기능(콘텐츠 발행·문의 접수·자동 발행)에는 방문자 로그인이 **필요 없으므로**, 묻지 않고 넣어서는 안 된다.

### 유형별 스택 라우팅 (질문의 결론)

> **공통 전제 (2026-07-22 개정):** 세 유형 **모두 Supabase 단일 스택**으로 구축한다.
> Payload는 더 이상 쓰지 않는다. 유형 차이는 "스택"이 아니라 **"방문자 로그인·결제 모듈을 붙이느냐"** 뿐이다.

| 유형 | 안내할 스택 | 이유 |
|------|------------|------|
| ① **로그인 필요 없는 자사/로컬 비즈니스 홈페이지** (GEO·문의 중심 — 병의원·법률·학원·시공 등) | ✅ **Supabase 단일** — Vercel(프론트)+Supabase(DB·관리자)+R2, 방문자 로그인 없음 | 콘텐츠 대량 발행 관리자는 [04_supabase_참고구현](04_supabase_참고구현/)으로 직접 구축. GEO 자동발행 로직 그대로. **이 참고자료의 기본 경로** |
| ② 홈페이지 + **방문자 회원 기능** (결제는 없음 — 내 문의/예약 조회, 회원 전용 콘텐츠) | ✅ **Supabase 단일** + 방문자 카카오/구글 로그인 추가 | 관리자·GEO·방문자 인증이 모두 Supabase 한 곳 → CP-1~3 진행. 문의 폼에 `user_id` 연결 |
| ③ **결제 서비스가 중심** — 강의 판매·자사몰(이커머스)·구독·포인트 | ✅ **Supabase 단일 풀스택** + 결제·주문·권한 모듈 | 회원 계정·주문·결제·권한이 **한 몸으로 강결합** → Auth+DB+RLS가 한 곳에 있어야 환불 트랜잭션·권한 부여·마이페이지가 깔끔. "돈이 움직이는 테이블 ★★★" 모듈(원장·환불·KPI) 추가 |

> 세 유형 모두 관리자 페이지는 [04_supabase_참고구현](04_supabase_참고구현/) 기반. ②는 방문자 소셜 로그인, ③은 결제 모듈을 그 위에 얹는다.

**질문 스크립트 (예시 포함해서 이렇게 물을 것):**

> 이 홈페이지는 어떤 유형에 가까울까요?
>
> **① 로그인 없는 자사 홈페이지** — 방문자는 글을 읽고 전화·문의 폼으로 연락하면 끝. (GEO 콘텐츠 발행이 목적이면 대부분 여기) → **Supabase로 진행합니다.** 방문자 로그인은 없이(개인정보 부담 최소), 관리자 페이지와 GEO 자동발행만 Supabase로 구축합니다.
>
> **② 회원 기능은 필요하지만 결제는 없음** — 예시: 내 문의/상담 내역 조회, 예약 조회·변경(노쇼 감소), 회원 전용 콘텐츠(재방문 유도), 후기·댓글, 카카오 채널 마케팅 DB, 문의 폼 자동 채움 → **Supabase + 방문자 카카오/구글 로그인**을 붙입니다.
>
> **③ 결제가 있는 서비스** — 예시: 강의 판매(수강권한·수강 페이지), 자사몰(장바구니·주문·배송), 구독·멤버십 → **Supabase 풀스택**으로 안내합니다. 주문·환불·권한이 회원 계정과 한 몸이라 이 조합이 맞고, 관리자 페이지는 04 참고구현 + 결제·주문 모듈로 확장합니다.
>
> 나중에 유형이 바뀌면(②→③ 등) 그때 확장할 수도 있습니다.

**답에 따른 진행 (세 유형 모두 Supabase — CP-1은 공통 필수):**

| 답 | 진행 |
|-----|------|
| **①** | CP-1(Supabase DB·관리자 인증) 진행 → CP-2·3(방문자 소셜) **생략** → CP-4(R2)~CP-5. 04 참고구현으로 관리자 구축 |
| **②** | CP-1(Supabase) → CP-2(구글) → CP-3(카카오) 진행. 문의 폼에 `user_id` 연결 |
| **③** | CP-1~3 진행 + 결제·주문·권한 모듈("돈이 움직이는 테이블") 추가. GEO 원칙(01)·용어(03)·04 참고구현·R2(CP-4)는 그대로 |
| 유보 | ①로 시작하되 문의 폼에 `user_id` 자리만 남겨둠(nullable) → 도입 시 CP-2·3 실행 |

> ⚠️ **변경점:** 구버전은 유형①에서 CP-1(Supabase)을 생략했으나, 이제 **관리자·DB 자체가 Supabase**이므로 유형①도 **CP-1은 필수**다. 생략되는 건 방문자 소셜 로그인(CP-2·3)뿐이다.

## 1. ★ AI 빌더 운영 규칙 — "단계 도달 시 요청" 프로토콜

이 참고문서들로 사이트를 구축하는 AI는 다음을 지킨다:

1. **키·시크릿을 한 번에 몰아서 요구하지 않는다.** 아래 §2 체크포인트 표의 해당 단계에 **도달했을 때**, 그 단계에 필요한 정보만 요청한다.
2. 요청할 때는 반드시 **[① 지금 이 단계에서 무엇을 만드는지 → ② 사용자가 어느 콘솔에서 무엇을 해야 하는지(클릭 단위 가이드) → ③ 받아야 할 값 목록]** 순서로 안내한다. 사용자는 비개발자일 수 있다.
3. **비밀값 취급:** 모든 키는 `.env`(로컬)와 배포 플랫폼 환경변수에만 저장. 코드·문서·채팅 로그에 하드코딩 금지. `service_role` 키와 R2 Secret은 **서버 전용** — 브라우저 번들에 절대 노출 금지 (`NEXT_PUBLIC_` 접두어 금지).
4. **각 단계 완료 시 검증부터:** 표의 "검증" 열을 실제로 실행해 통과를 확인한 뒤 다음 단계로 넘어간다.
5. **콘솔 UI는 자주 바뀐다:** 각 단계 착수 전에 §9의 공식 문서를 먼저 조회(WebFetch/Context7)해 최신 절차와 대조한다. 이 문서의 절차와 다르면 공식 문서를 따른다.

## 3. CP-1: Supabase 프로젝트 (인증·DB 기반)

**사용자 가이드:**
1. [supabase.com](https://supabase.com) 가입 → **New project** (리전: **Northeast Asia (Seoul)** 선택 — 성능 체크리스트의 "서버 리전 = DB 리전"과 맞춤)
2. 프로젝트 생성 후 **Settings → API** 에서 세 값을 복사:
   - `Project URL` (예: `https://xxxx.supabase.co`)
   - `anon` `public` 키 (브라우저용 — 공개 가능)
   - `service_role` 키 (**서버 전용 — 절대 노출 금지**)

**AI가 요청할 값:** 위 3개.
**AI가 할 일:** `.env`에 기록, 클라이언트 유틸(`lib/supabase`) 생성, 접속 검증.

## 4. CP-2: 구글 로그인 (Google OAuth)

**사전 지식:** 소셜 로그인의 콜백 주소는 Supabase가 받는다 →
`https://<프로젝트ref>.supabase.co/auth/v1/callback` (Supabase 대시보드 **Authentication → Providers → Google** 화면에 표시됨. 이 값을 복사해 구글 콘솔에 등록)

**사용자 가이드:**
1. [console.cloud.google.com](https://console.cloud.google.com) → 프로젝트 생성(또는 선택)
2. **APIs & Services → OAuth consent screen** — 앱 이름·지원 이메일 입력, External로 게시
3. **APIs & Services → Credentials → + Create Credentials → OAuth client ID**
   - Application type: **Web application**
   - **Authorized redirect URIs**에 위 Supabase 콜백 URL 붙여넣기
4. 생성된 **Client ID / Client Secret** 복사
5. Supabase 대시보드 **Authentication → Providers → Google** 활성화 → 두 값 붙여넣기 → Save

**AI가 요청할 값:** Client ID, Client Secret (또는 사용자가 Supabase 콘솔에 직접 입력했다는 확인).
**AI가 할 일 (프론트 코드):**
```ts
await supabase.auth.signInWithOAuth({
  provider: 'google',
  options: { redirectTo: `${location.origin}/auth/callback` },
})
```
**검증:** 로컬에서 구글 로그인 → 세션 발급 → 유저 이메일 화면 표시 1회 확인.

## 5. CP-3: 카카오 로그인 (Kakao OAuth)

**사용자 가이드:**
1. [developers.kakao.com](https://developers.kakao.com) → **내 애플리케이션 → 애플리케이션 추가**
2. **앱 키** 중 **REST API 키** 복사 (← Supabase의 Client ID로 쓰임)
3. **제품 설정 → 카카오 로그인 → 활성화 ON**
4. **Redirect URI 등록:** `https://<프로젝트ref>.supabase.co/auth/v1/callback` (Supabase Providers → Kakao 화면에서 복사)
5. **카카오 로그인 → 동의항목:** 닉네임·프로필 + **카카오계정(이메일)** 동의 설정 (이메일은 비즈 앱 전환/검수 필요할 수 있음 — 콘솔 안내를 따름)
6. **제품 설정 → 카카오 로그인 → 보안 → Client Secret 발급** → 활성화 ON → 복사
7. Supabase 대시보드 **Authentication → Providers → Kakao** 활성화 → REST API 키 + Client Secret 입력 → Save

**AI가 요청할 값:** REST API 키, Client Secret (또는 Supabase 콘솔 직접 입력 확인).
**AI가 할 일:** `signInWithOAuth({ provider: 'kakao', ... })` 버튼 구현.
**검증:** 카카오 로그인 → 세션 발급 1회 확인. (이메일 동의 미설정 시 email이 null로 오는 것까지 확인)

## 6. CP-4: Cloudflare R2 (이미지·영상 저장소)

**개념:** R2는 S3 호환 오브젝트 스토리지. **송신(egress) 무료**라 이미지·영상 서빙에 유리. S3 SDK를 그대로 쓰되 endpoint만 바꾼다.

**사용자 가이드:**
1. [dash.cloudflare.com](https://dash.cloudflare.com) → **R2** → 플랜 활성화(무료 티어 있음) → **Create bucket** (예: `site-media`, 리전 자동)
2. **계정 ID(Account ID)** 확인 (R2 개요 화면 우측)
3. **R2 → Manage R2 API Tokens → Create API Token** — 권한 **Object Read & Write**, 대상 버킷 지정 → 생성된 **Access Key ID / Secret Access Key** 복사 (Secret은 이때 한 번만 보임)
4. **공개 서빙 설정 (이미지·영상을 방문자가 보는 경로):**
   - 정식: 버킷 **Settings → Custom Domains**에 서브도메인 연결 (예: `media.내도메인.com`) ← 운영 권장 (캐시·속도)
   - 임시: **r2.dev** 공개 URL 활성화 (개발 확인용 — 속도 제한 있어 운영 비권장)
5. (브라우저에서 직접 업로드할 경우) 버킷 **Settings → CORS policy**에 사이트 도메인 허용 규칙 추가

**AI가 요청할 값:** Account ID, Access Key ID, Secret Access Key, 버킷명, 공개 도메인(또는 r2.dev URL).
**S3 호환 endpoint (AI가 조립):** `https://<AccountID>.r2.cloudflarestorage.com`, region은 `auto`.

**연동 방법 (Supabase 단일):**

| 방식 | 연동 |
|------|------|
| **서버 업로드 (기본)** | 관리자 페이지의 서버 액션/라우트에서 S3 SDK(`@aws-sdk/client-s3`)로 R2에 업로드 (endpoint = 위 R2 주소, region `auto`, `forcePathStyle: true`) → `media` 테이블엔 공개 URL·alt만 저장 |
| **브라우저 직행 (대용량·영상)** | presigned URL 발급 → 브라우저 → R2 직행 업로드 (부록 A 이미지 업로드 패턴). 서버 body 제한 회피 |

> 참고: Supabase Storage를 쓸 수도 있으나, egress 무료·커스텀 도메인 캐시 때문에 **미디어 서빙은 R2로 확정**. Supabase Storage는 선택적 대안.

**영상 주의:** 대용량(수십 MB↑)은 서버 액션 body 제한에 걸리므로 **presigned URL로 브라우저 → R2 직행 업로드**가 정석. 서빙은 커스텀 도메인 + Cloudflare 캐시.

**검증:** 파일 1개 업로드 → 공개 도메인 URL로 브라우저에서 열림 확인. (비공개 자원이면 presigned GET으로 확인)

## 7. 아키텍처에 얹으면 (02 문서와의 관계)

```
방문자 ──카카오/구글 로그인(②③)──▶ Supabase Auth (세션)
방문자 ──이미지·영상 조회──▶ media.도메인.com (R2 + Cloudflare 캐시)
관리자 ──파일 업로드──▶ 관리자페이지 미디어(5장) ──▶ R2 버킷
관리자 ──로그인──▶ Supabase Auth + profiles.role=admin (RLS is_admin())
자동발행 스케줄러 ──상주 폴링(Railway)──▶ Supabase에 service_role로 write
```

- 02 문서 5장 "미디어"의 저장소 = **R2로 확정.** (media 테이블엔 메타만, 파일은 R2)
- 02 문서 6.4 "DB 백업"의 저장 위치도 **같은 R2** (`backups/db/<시각>/` 경로) — 단, 백업엔 개인정보가 포함되므로 **공개 도메인에 연결되지 않는 비공개 경로/버킷**을 쓰고 다운로드는 단기 서명 URL로만. CP-4에서 토큰 발급 시 이 용도를 함께 고려. (Supabase는 자체 백업도 제공하나, R2 논리 백업을 병행하면 스택 독립성 확보)
- 02 문서 4.5 문의 접수함: 비회원 접수는 로그인 불필요(익명 insert — RLS `for insert with check (true)`). 회원이 "내 문의 내역"을 보려면 Supabase 세션의 `user_id`를 문의에 연결. **읽기는 관리자(is_admin())만** — 연락처 개인정보 보호.
- GEO와의 관계: 인증·저장소는 GEO에 직접 영향 없음. 단 **이미지 공개 URL이 안정적이어야**(커스텀 도메인) OG 이미지·JSON-LD `logo`/`image`가 봇에게 깨지지 않는다.

## 8. 환경변수 총정리 (.env)

```bash
# CP-1 Supabase
NEXT_PUBLIC_SUPABASE_URL=https://xxxx.supabase.co
NEXT_PUBLIC_SUPABASE_ANON_KEY=eyJ...        # 브라우저 공개 OK
SUPABASE_SERVICE_ROLE_KEY=eyJ...            # ★서버 전용, NEXT_PUBLIC_ 금지

# CP-2/3 소셜 로그인 — 키는 Supabase 대시보드에 저장되므로 앱 env에는 불필요
# (직접 OAuth를 구현하는 예외 경우에만 별도 보관)

# CP-4 Cloudflare R2
R2_ACCOUNT_ID=...
R2_ACCESS_KEY_ID=...                        # ★서버 전용
R2_SECRET_ACCESS_KEY=...                    # ★서버 전용
R2_BUCKET=site-media
NEXT_PUBLIC_MEDIA_URL=https://media.내도메인.com   # 공개 서빙 도메인

# 자동발행 스케줄러 (Railway 상주 — §7 발행 워크플로)
GEMINI_API_KEY=...                          # ★서버 전용, 리라이팅 LLM
# 스케줄러는 SUPABASE_SERVICE_ROLE_KEY로 Supabase에 직접 write (위 CP-1 값 재사용)
```

> **변경점 (2026-07-22):** 구버전의 `DATABASE_URI`/`PAYLOAD_SECRET`(Payload/Railway DB)은 **제거**됨.
> 이제 DB는 Supabase가 보유하므로 앱은 Supabase 키만 있으면 된다. Railway는 스케줄러 실행 컨테이너로만 쓰고, 그 스케줄러도 `SUPABASE_SERVICE_ROLE_KEY`로 Supabase에 접근한다.
