# build.md — AI 빌더 실행 대본 (★가장 먼저 읽는 파일)

> **AI에게:** 이 폴더(GEO_참고자료)를 받았다면 **이 파일을 먼저 끝까지 읽고, 아래 STEP을 순서대로 실행**하라.
> 각 STEP은 [① 무엇을 → ② 어느 문서 참조 → ③ 검증(failable) → ④ 통과해야 다음]으로 되어 있다.
> **검증을 통과하지 못하면 다음 STEP으로 넘어가지 마라.** "된 것 같다"로 넘기지 말고 실제로 실행해 관찰하라.
>
> ### 🚦 가장 먼저 할 일 (사용자와의 첫 대화)
> 코드를 짜기 전에, **STEP 0(사이트 유형 질문) → STEP 0.5(입력 요청서)** 부터 사용자에게 제시하라.
> 즉 첫 응답은 "사이트 유형이 ①/②/③ 중 무엇인가?"를 묻고, 답을 받으면 STEP 0.5의 항목을 **문답식으로 하나씩 물어** 정보를 수집하는 것이다.
> **Supabase·키·코드 작업(STEP 1~)은 이 정보를 다 받은 뒤에 시작**한다. 정보 없이 인프라부터 만들지 마라.

## 0. 이 kit이 만드는 것 (한 눈에)

**GEO(생성형 검색 최적화) 특화 홈페이지** = 프론트(방문자·봇이 읽음) + 관리자페이지(운영자가 콘텐츠 관리) + 네이버 자동발행.

**확정 스택:** Supabase(Postgres+Auth+RLS) + Next.js(Vercel) + R2(미디어) + Railway(자동발행 스케줄러).

```
STEP 0    사이트 유형 질문 (CP-0)
STEP 0.5  요구사항 입력 + 디자인 해체            → 검증: 필수항목 수집 + Build Prompt + 상호명 유출 grep 0건 계획
STEP 1    Supabase 프로젝트 + schema.sql          → 검증: 테이블 생성
STEP 2    관리자 계정 (is_admin)                   → 검증: 로그인
STEP 3    프론트 구현 (디자인 + GEO 요소 SSR)     → 검증: <head>에 robots/JSON-LD + 모바일 + 상호명 grep 0건 + alt 0건
STEP 4    R2 미디어 (CP-4)                         → 검증: 업로드→공개 URL + alt 필수값 거부
STEP 5    관리자 UI (02 청사진)                    → 검증: 글 1건 CRUD + og:image·JSON-LD image
STEP 6    네이버 리라이팅 (05)                     → 검증: 초안 1건 생성
STEP 7    자동발행 스케줄러 (04 scheduler)          → 검증: 1 tick 발행
STEP 8    배포 (CP-5)                              → 검증: 프로덕션 SSR JSON-LD
STEP 9    ★검색엔진·AI봇 노출 개통                 → 검증: robots/llms/sitemap 응답 + 소유확인 2건 통과
          (robots·llms·사이트맵 + 구글 서치콘솔
           + 네이버 서치어드바이저 + GBP)
```

> **⚠️ STEP 9를 빼먹지 마라 — "만들었다"와 "노출된다"는 다르다.**
> STEP 8까지는 잘 만든 사이트가 서버에 올라간 것뿐이고, **봇은 아직 이 사이트의 존재를 모른다.**
> 등록·제출까지 해야 검색과 AI 답변에 나타나기 시작한다. 사용자가 묻지 않아도 **배포 직후 먼저 안내**하라.

> **⚠️ 미디어(R2)는 "글을 쓰는 모든 STEP"보다 먼저다 (린 피부과 1·2차에서 두 번 보정).**
> 이유 ①: STEP 6의 크롤링은 [05 부록 D-7]에 따라 **이미지를 의도적으로 제외**한다(핫링크 불안정 + 환자 실사진·워터마크 저작권).
> 이유 ②: **발행 글은 대표 이미지(OG image)가 필수**다 — 없으면 `og:image`·JSON-LD `image`·목록 썸네일이 전부 빈다.
> 따라서 R2를 **관리자 UI(글쓰기)보다 먼저** 뚫는다. 순서가 뒤집히면 "이미지를 넣을 수단이 없는 글"이 쌓이고, 나중에 전 글을 되돌아가 채워야 한다.
> (1차에서는 R2가 자동발행 뒤에 있었고, 2차에서 다시 글쓰기 뒤에 있는 문제가 드러나 여기까지 당겼다.)

## ★ 실행 전 필수 규칙 (06 §1 프로토콜)

1. **키·시크릿은 한 번에 몰아 요구하지 말 것.** 각 STEP에 도달했을 때, 그 STEP에 필요한 값만 요청한다.
2. 요청 시 반드시 **[① 지금 뭘 만드는지 → ② 어느 콘솔에서 뭘 클릭하는지 → ③ 받을 값 목록]** 순으로 안내. 사용자는 비개발자일 수 있다.
3. `service_role` 키·R2 Secret은 **서버 전용** — 브라우저 번들 노출 금지(`NEXT_PUBLIC_` 접두어 금지).
4. **콘솔 UI는 자주 바뀐다.** 각 STEP 착수 전 [06 §9]의 공식 문서를 WebFetch로 최신 대조. 문서와 다르면 공식 문서를 따른다.
5. **각 STEP은 검증부터 통과.** 아래 "검증" 항목을 실제로 실행해 통과를 확인한 뒤 다음으로.

### ★ AI 지시: 아래 항목을 **문답식으로 하나씩(묶음씩) 대화하며** 수집하라

> **양식 한 장을 통째로 던지지 마라.** 사용자는 비개발자일 수 있다. **A→B→…→G 순서로 묶음별로 물어보고, 답을 받으면 다음 묶음으로** 넘어간다. 한 번에 3~5개 항목씩(한 묶음)만 물어 부담을 줄인다.
>
> **진행 규칙:**
> - 각 묶음을 물을 때 **왜 필요한지 한 줄 + 예시**를 곁들인다 (예: "AI가 '강남 근처 피부과' 질문에 답하려면 정확한 주소가 필요해요").
> - 사용자가 "모름"이라 하면 **넘어가되 대안을 제시**한다 (위경도 모름→주소로 조회 / sameAs 없음→프로필 페이지 대체 + E-E-A-T 약화 고지 / 도메인 미정→BASE_URL 상수).
> - **A·B·C는 최소 필수** — 비면 다음으로 안 넘어가고 다시 묻는다. D~G는 "지금 없으면 나중에 보강 가능"이라 안내하고 진행해도 된다.
> - 답이 모이면 **한 번 정리해 보여주고 "이대로 진행할까요?" 확인**받은 뒤 디자인 해체로 넘어간다.

**수집 항목 (묶음 단위 · AI가 대화로 하나씩 질문):**

| 묶음 | 항목 | 물을 때 곁들일 것 |
|---|---|---|
| **A. 기본 정체성** | 업종 / 상호명(한글·영문) / 지역 / 사업자번호(선택) | 업종은 스키마 @type을 정함 |
| **B. 벤치마킹 & 개요** | 벤치마킹 사이트 URL(1개+) / 만들려는 사이트 개요(목적·톤·강조점) | URL은 디자인 해체 대상 |
| **C. NAP + 로컬** | 도로명 주소 / 대표 전화 / 영업시간 / 위경도(모르면 조회) / 가격 안내 방식 | GEO 핵심 — AI "근처/영업중" 답변용 |
| **D. 서비스 & 키워드** | 주요 시술/서비스 목록 / GEO 타겟 키워드(지역+시술) | 각 서비스가 상세페이지가 됨 |
| **E. 대표 프로필** | 이름·직책 / 경력·학력 / 전문분야 / **sameAs**(실존 본인 링크) | author E-E-A-T. sameAs는 가짜·타인 금지 |
| **F. 외부 채널 & 도메인** | SNS·GBP·네이버플레이스 / 도메인(미정 가능) | sameAs·NAP 동기화 |
| **G. 자동발행(선택)** | 연동 네이버 블로그 ID(본인 소유) | 없으면 나중에 추가 |

> 시작 멘트 예: *"홈페이지를 만들기 위해 몇 가지 여쭤볼게요. 한 번에 다 아니고 하나씩 물어볼 테니 편하게 답해주세요. 모르는 건 '모름'이라고 하시면 제가 대안을 찾을게요. 먼저 **어떤 업종이고 상호명·지역이 어떻게 되나요?**"*

### 받아야 할 항목의 근거 (AI 참고 — 왜 이 정보가 필요한가)

> 위 요청서의 각 항목은 GEO JSON-LD·author E-E-A-T·자동발행에 **반드시 필요한 데이터**다. 근거: 내부 02 설계 §3.1/4.2 + LocalBusiness 스키마 3소스 교차검증(NAP·hours·geo·sameAs 필수).

**A. 기본 정체성**
- 업종 (→ 스키마 `@type`: 병원=MedicalClinic/Hospital, 일반=LocalBusiness)
- 상호명 (한글/영문)
- 지역
- 사업자번호 (선택)

**B. 벤치마킹 & 디자인**
- 벤치마킹할 사이트 URL (1개 이상 — 디자인 해체 대상)
- 만들려는 사이트 개요 (한두 문단: 목적·톤·핵심 강조점)

**C. NAP + 로컬 신호 (GEO 핵심 — AI "near me/open now" 답변용)**
- 정확한 도로명 주소
- 대표 전화번호
- 영업/진료 시간
- 위경도 좌표 (모르면 주소로 추후 조회)
- 가격대(priceRange) 또는 비용 안내 방식

**D. 서비스 & 키워드**
- 주요 시술/서비스 목록 (→ 상세페이지 + Service 스키마)
- GEO 타겟 키워드 (지역+시술/증상 조합)

**E. 대표 프로필 (author E-E-A-T)**
- 이름 / 직책
- 경력·학력 (bio, alumniOf)
- 전문분야
- **sameAs**: 실존 본인 외부 링크 (LinkedIn·논문·유튜브·프로필) — ⚠️ 가짜·타인 프로필 금지

**F. 외부 채널 & 도메인**
- SNS·외부 채널 (인스타·카카오채널·Google Business Profile·네이버플레이스) — sameAs + NAP 동기화
- 도메인 (미정이면 BASE_URL 상수로 분리해 배포 시 교체)

**G. 자동발행 (선택 — STEP 7에서 씀)**
- 연동할 네이버 블로그 ID (본인 소유)

### 디자인 해체 실행 — ★사이트 전체를 템플릿으로 (하위페이지 전수)

> **메인 페이지만 보지 마라.** 벤치마킹 URL의 **하위페이지까지 전부 훑어 "템플릿"으로 뽑는다.** 이 템플릿들이 곧 내 홈페이지의 페이지 골격이 된다. [사이트-디자인-해체-프롬프트.md](사이트-디자인-해체-프롬프트.md)의 **§멀티 페이지 모드(Phase 1~5)를 반드시 실행**한다.
>
> 🚫 **임의 생성 절대 금지 — [벤치마킹-실전-해부가이드.md](벤치마킹-실전-해부가이드.md)의 "규칙 0"을 먼저 읽고 그대로 따르라.** 값·섹션·속도·색·폰트를 **생각해서 넣지 마라.** 전부 원본 소스(HTML/CSS/JS)에서 **실측한 값만** 쓴다. `curl`로 raw 소스 받기(A) → CSS 토큰·애니속도 실측(B) → 섹션 전수(C) → 인터랙션 JS 정독(D) → **코딩 전 실측값 대조표(SPEC SHEET) 100% 채우기(D.5)** → Playwright 렌더 검증(E). WebFetch 요약은 방향 감각용일 뿐 재현 재료 금지. **목표는 벤치마킹 사이트와 99% 동일 재현, 한 번에.**
>
> ⚙️ **실측은 손으로 하지 말고 [벤치마킹-실측-스크립트/](벤치마킹-실측-스크립트/)의 py 4종을 돌려라.** 1=색·폰트·애니속도·섹션순서 / 2=리빌·인터랙션 / 3=섹션별 구조 / 4=정밀 CSS. 이대로 돌리면 SPEC SHEET가 채워진다. (실행법은 해당 폴더 README)

**실행 순서 (디자인 해체 문서 멀티페이지 모드 그대로):**
1. **Phase 1 — 사이트맵 수집:** GNB/푸터/sitemap.xml에서 **전체 페이지 URL 트리**를 추출. (하위페이지 누락 금지 — 실제로 링크를 따라 들어가 확인)
2. **Phase 2 — 템플릿 분류:** 페이지들을 레이아웃 **템플릿 단위**로 묶는다 (예: 메인 / 시술상세 / 이벤트목록 / 의료진 / 오시는길). 유형별 2개 페이지를 열어 마크업이 같은지 확인. *(수십 페이지라도 템플릿은 보통 3~5개)*
3. **Phase 3 — 템플릿별 해체:** 유형별 대표 1개씩 측정값 기반 해체(hex·px·ms). 공통 셸(헤더/푸터/퀵메뉴)은 한 번만. 통이미지 본문이면 "콘텐츠 슬롯" 정의로 대체.
4. **Phase 4 — 콘텐츠 매트릭스:** 해체 안 한 나머지 페이지를 표로 (URL / 템플릿유형 / 제목 / 자산). 재현 시 각 행 = 템플릿 + 콘텐츠.
5. **Phase 5 — 링크 맵:** 클릭 요소의 출발→목적지 표. 재현 완료 기준 = 데드링크(`href="#"`) 0건.

**산출물 = 재사용 가능한 템플릿 세트:** Phase 3의 템플릿들이 STEP 3에서 내 홈페이지 페이지를 찍어내는 틀이 된다. (내 서비스 목록 D의 각 항목 → "시술상세 템플릿"으로 생성, 등)

### ★ RLS 검증 함정 2가지 (린 피부과 1차 실측 — 반드시 읽을 것)

> RLS는 "에러를 던져서" 막는 게 아니라 **"조용히 0행으로"** 막는 경우가 있다. 에러 유무로 판정하면 **통과했다고 오판**한다.

1. **update 차단은 에러가 아니라 0행 매칭이다.**
   anon이 막힌 행을 update하면 예외가 안 나고 `error: null` + 0행 영향으로 끝난다.
   → **에러 유무로 판정하지 마라. 실제로 값이 바뀌었는지 재조회해서 대조**해야 정확하다.
   (`if (!error) ok()` 로 짜면 차단됐는데 통과로 기록된다)

2. **`.insert().select()` 체이닝이 insert 정책을 통과하고도 실패한다.**
   `insert`는 허용, `select`는 admin 전용인 테이블(예: `inquiries` — 방문자는 넣기만, 읽기는 관리자만)에서
   `.insert(...).select()`로 체이닝하면 **insert 직후의 select가 RLS에 걸려 전체가 거부**된다.
   → 이런 테이블은 **`.select()` 없이 insert만** 할 것. (상담 폼이 정확히 이 케이스)

  5. **★이미지 alt 누락 grep 0건:** 정적 페이지(회사소개·시술상세 등)의 모든 `<img>`가 내용을 설명하는 alt를 가졌는지 **실패 가능한 검사로** 확인한다. "눈으로 봤다"는 검증이 아니다.
     ```bash
     # ① alt 속성이 아예 없는 img → 0건이어야 함
     grep -roE '<img(?![^>]*\balt=)[^>]*>' --include=*.tsx --include=*.html -P . | wc -l
     # ② alt=""(빈 값) → 장식용 이미지가 아니면 0건이어야 함
     grep -roE 'alt=""' --include=*.tsx --include=*.html . | wc -l
     # ③ alt에 파일명이 들어간 경우(잘못된 alt) → 0건
     grep -roE 'alt="[^"]*\.(jpg|jpeg|png|webp|svg)"' --include=*.tsx --include=*.html . | wc -l
     ```
     > 순수 장식 이미지는 `alt=""`가 **올바른** 처리다(스크린리더가 건너뜀). ②에서 걸린 건은 "장식이라 의도적으로 비웠다"를 **한 건씩 확인**하고, 콘텐츠 이미지면 채운다. 무심코 비운 것과 의도적으로 비운 것을 구분하는 게 이 검사의 목적이다.

### 🚨 8-0. Next.js 앱은 저장소 **루트**에 둔다 (STEP 3에서 결정되는 사항)

배포 플랫폼(Vercel·Railway·Netlify·Cloudflare)은 전부 **저장소 루트에서 `package.json`을 찾아**
프레임워크를 감지한다. 앱을 `web/` 같은 하위 폴더에 만들면 **어디에 올려도 같은 자리에서 막힌다.**

```
권장                            피할 것
저장소/                         저장소/
├── package.json  ← 자동감지    ├── web/
├── src/                        │   └── package.json  ← 루트에서 안 보임
├── supabase/                   ├── supabase/
└── design/                     └── design/
```

**실측 사고 (잭 피부과, 2026-08) — 하위 폴더로 만들었다가 겪은 것:**

| 플랫폼 | 증상 | 원인 |
|---|---|---|
| Vercel | 사이트 전체 404. `X-Vercel-Error: NOT_FOUND` + `Content-Type: text/plain` | 루트에 package.json이 없어 **빈 배포** 생성 |
| Vercel | Root Directory를 고친 뒤에도 `/`는 404, `/vercel.svg`만 200 | **Framework Preset이 `null`로 굳음** → `next build`는 돌지만 `public/`만 정적 서빙 |
| Railway | `railpack prepare` 단계에서 빌드 실패 | 루트에서 빌드 대상을 못 찾음 |

대시보드 설정(Root Directory)으로 우회할 수는 있으나 **플랫폼마다 매번 해야 하고, 빠뜨리면 위 증상이 그대로 난다.**
STEP 3에서 앱을 루트에 만들면 이후 어떤 플랫폼이든 설정 없이 동작한다.

> ⚠️ 이미 하위 폴더로 만들었다면 STEP 8 전에 루트로 옮겨라. 충돌하는 건 보통
> `.gitignore`와 `README.md` 둘뿐이다(병합). `supabase/`·`design/`은 빌드와 무관하므로 그대로 둔다.

> ⚠️ **Framework Preset도 확인하라.** 한 번 `Other/null`로 잡히면 구조를 고쳐도 자동으로 안 바뀐다.
> 증상이 특이하다 — 빌드 로그에는 `next build` 성공이 찍히는데 `/`만 404다.

### 9-A. robots.txt — "들어와도 되는가" (출입 허가)

STEP 3에서 이미 깔았어야 한다. 여기서는 **프로덕션에서 실제로 열리는지 확인**하고 누락 봇을 보강한다. [01 §5.1]의 AI 크롤러 9종 + 네이버 + 사이트맵 줄이 있어야 한다.

```txt
User-agent: *
Allow: /

# AI 크롤러 (01 §5.1 — 9종)
User-agent: GPTBot            # OpenAI 학습·인덱스
User-agent: OAI-SearchBot     # OpenAI 검색
User-agent: ChatGPT-User      # OpenAI 브라우징
User-agent: ClaudeBot         # Anthropic
User-agent: anthropic-ai      # Anthropic (legacy)
User-agent: Google-Extended   # Google Gemini / Vertex
User-agent: PerplexityBot     # Perplexity
User-agent: Applebot-Extended # Apple Intelligence
User-agent: CCBot             # Common Crawl (다수 LLM 데이터 소스)
Allow: /

User-agent: Yeti              # 네이버 [미검증 — 9-E 주석 참조]
Allow: /

Sitemap: https://{도메인}/sitemap.xml
Sitemap: https://{도메인}/rss
# LLM guidance file: https://{도메인}/llms.txt
```

> **`Sitemap:` 줄에 RSS도 넣는다.** 콘솔에 수동 제출도 하지만 그건 사람이 잊을 수 있다.
> robots.txt에 적어두면 봇이 스스로 찾아간다.

### 9-A-2. ★sitemap.xml · rss — "무엇이 있고, 무엇이 새로 올라왔나"

두 파일은 **역할이 다르다. 둘 다 있어야 한다.**

| | sitemap.xml | rss |
|---|---|---|
| 답하는 질문 | 이 사이트에 **어떤 페이지가 있나** | **새 글이 올라왔나** |
| 담는 것 | 홈·센터·시술상세·일반페이지·**블로그 글 전부** | 최근 발행 글 (50건 내외) |
| 제출처 | 구글 서치콘솔 · 네이버 서치어드바이저 | 구글 서치콘솔 · **네이버 서치어드바이저(별도 단계)** |

**🚨 실측 사고 2건 (린 피부과 / 잭 피부과 — 둘 다 STEP 9에서야 발견됨):**

1. **RSS 라우트를 아예 안 만들었다.** 이 문서 어디에도 RSS를 만들라는 지시가 없었기 때문이다.
   네이버 서치어드바이저는 RSS 제출이 **독립 단계**라, 없으면 상태값이 `가져올 수 없음`에서
   영원히 안 넘어간다. 운영자는 며칠을 기다리다 포기한다.
2. **사이트맵에 블로그 글이 통째로 빠져 있었다.** 시술·센터·일반페이지만 넣고
   `/blog`·`/blog/[slug]`를 빠뜨렸다. STEP 6·7로 자동발행을 아무리 돌려도
   **그 결과물이 검색엔진 목록에 없다** — 파이프라인 전체가 헛돈다.

→ **STEP 3에서 sitemap을 만들 때 블로그를 포함시키고, rss 라우트를 같이 만들어라.**
   두 곳이 **같은 조회 함수**를 쓰게 해야 한쪽에만 빠지는 일이 안 생긴다.

**RSS 만들 때 실수하기 쉬운 것:**
- `pubDate`는 **RFC-822**(`Tue, 12 Aug 2026 09:00:00 GMT`)여야 한다.
  ISO 문자열(`2026-08-12T09:00:00Z`)을 넣으면 봇이 날짜를 못 읽는다. JS는 `toUTCString()`.
- `content-type`은 `application/rss+xml`. `text/html`로 나가면 피드로 인식되지 않는다.
- 제목에 `&`·`<`가 들어가면 피드 전체가 깨진다 — XML 이스케이프 필수.
- `<atom:link rel="self">`로 피드 자기 주소를 선언한다.
- **초안(draft)이 절대 들어가면 안 된다** — 사이트맵도 마찬가지.

### 9-D. ★네이버 서치어드바이저 등록 (국내 사이트 필수)

**구글 등록으로 대체되지 않는 별도 축이다.** 이 kit은 STEP 6·7에서 **네이버 블로그 자동발행**을 핵심 기능으로 쓰는데, 홈페이지 본체가 네이버에 등록돼 있지 않으면 **네이버 검색에서 안 잡힌다** — 파이프라인 앞뒤가 안 맞는다.

- ⑦ **요청 → 사이트맵 제출**에 `https://{도메인}/sitemap.xml`
- ⑧ **URL 검사 → 수집요청**으로 주요 페이지를 직접 등록
  - 초반에 **`수집 보류`** 가 떠도 정상이다. 발행량이 쌓이면 수집 성공으로 넘어간다 —
    사용자에게 미리 알려라. 모르면 잘못된 줄 알고 설정을 뒤진다.

**소유확인 메타 넣는 법 — Next.js는 네이버 전용 필드가 없다:**

`verification` 필드는 **google/yandex/yahoo만 전용 지원**한다(공식 문서 확인). **네이버는 `verification.other`로 넣는다:**

```ts
// app/layout.tsx
export const metadata: Metadata = {
  verification: {
    google: process.env.NEXT_PUBLIC_GOOGLE_SITE_VERIFICATION,
    other: {
      // ★네이버 전용 필드 없음 → other로. <meta name="naver-site-verification" content="..."> 출력됨
      'naver-site-verification': process.env.NEXT_PUBLIC_NAVER_SITE_VERIFICATION ?? '',
    },
  },
}
```

- **검증 (failable) — 8개 다 통과해야 "개통 완료":**
  1. `curl -s https://{도메인}/robots.txt` → AI 크롤러 Allow + `Sitemap:` 줄 **2개**(sitemap.xml·rss) 출력.
  2. `curl -s https://{도메인}/sitemap.xml | head` → XML이 나오고 URL이 **실제 페이지 수만큼** 들어있는가.
  2-1. **★사이트맵에 블로그 글이 들어있는가** — 발행 글 수와 `<loc>…/blog/…` 개수를 대조하라.
     ```bash
     curl -s https://{도메인}/sitemap.xml | grep -c '/blog/'   # 발행 글 수와 같아야 한다
     ```
     0이면 자동발행 결과물이 통째로 색인 대상 밖이다 → 9-A-2 참조.
  2-2. **★`/rss`가 RSS 2.0으로 열리는가**
     ```bash
     curl -sI https://{도메인}/rss | grep -i content-type   # application/rss+xml 이어야 한다
     curl -s  https://{도메인}/rss | grep -o '<pubDate>[^<]*' | head -1
     # → "Tue, 12 Aug 2026 09:00:00 GMT" 형태(RFC-822). ISO면 봇이 날짜를 못 읽는다
     ```
  2-3. **초안이 sitemap·rss 어디에도 없는가.** ⚠️ 확인은 **관리자 세션으로** 하라 —
     비로그인으로 DB를 조회하면 RLS가 초안을 가려서 "샜는지" 자체를 볼 수 없다.
     못 보는 검사는 통과해도 의미가 없다.
  3. `curl -s https://{도메인}/llms.txt` → 텍스트 출력 (오류면 미설정 = GEO 미적용 신호, [01 §5.2]).
  4. 소유확인 메타가 **2개**(구글·네이버) SSR로 나오는가.
     ⚠️ `grep -c`를 쓰지 마라 — 그건 **매칭된 줄 수**를 센다. Next.js는 `<head>`를 한 줄로
     압축하므로 둘 다 있어도 `1`이 나온다. 또 RSC 페이로드에 같은 문자열이 한 번 더 실려
     단순 문자열 카운트는 4가 나온다. **meta 태그만** 세야 한다.
     ```bash
     curl -s https://{도메인} | grep -oE '<meta name="[a-z]+-site-verification"' | wc -l
     # → 2 여야 통과. 0·1이면 SSR 출력 실패
     ```
     ⚠️ `NEXT_PUBLIC_` 값은 **빌드 시점에 HTML로 구워진다.** 환경변수만 넣고 재배포하지
     않으면 태그가 안 나온다 — 값을 넣었는데 0건이면 십중팔구 재배포를 안 한 것이다.
  5. **두 콘솔에서 "소유확인" 버튼이 실제로 성공**하는가. ⚠️ "태그 넣었으니 됐다"로 넘기지 마라 — **버튼을 눌러 통과를 관찰**해야 검증이다.
  6. 사이트맵 제출 후 콘솔에 **수집 요청이 접수 상태**로 뜨는가. (색인 자체는 시간이 걸리므로 "접수"까지가 이 STEP의 통과 기준)

> **개통 후 안내할 것 (사용자에게):** 색인은 **즉시가 아니다.** 구글은 보통 수일~수 주, 네이버는 며칠. 다만 [05](05_네이버_리라이팅_참고구현.md)에 따르면 **AI 검색 엔진은 발행 후 약 2일 내** 인용을 시작한다(전통 SEO 색인은 수 주). 확인법은 `site:{도메인}` 검색([01 §11.2]) — 결과가 없으면 미색인이다. 조급하게 재제출을 반복하지 말고 1~2주 뒤 확인하라고 알려라.

- **검증 (failable) — 3개:**
  1. `curl -s https://{도메인} | grep naver-site-verification` → **1건 출력**. (0건이면 메타가 SSR로 안 나온 것)
  2. 네이버 서치어드바이저 콘솔에서 **"소유확인" 버튼이 성공**하는가. (버튼을 누르지 않고 "태그 넣었으니 됐다"로 넘기지 마라 — 실제로 통과해야 한다)
  3. 사이트맵 제출 후 콘솔에 **수집 요청이 접수 상태로 뜨는가.** 색인은 시간이 걸리므로 "접수"까지가 이 STEP의 통과 기준이다.

## ⚠️ 전 STEP 공통 — 하지 말 것

- blogs에 직접 insert 금지 → 반드시 `saveBlogWithJsonLd()` 경유 (JSON-LD 누락 방지).
- **대표 이미지 없이 발행 금지.** `og:image`·JSON-LD `image`·목록 썸네일이 한꺼번에 빈다. draft는 허용, published는 필수 — `saveBlogWithJsonLd()`가 가드한다.
- **alt 없는 이미지 금지.** 업로드 시 필수값으로 강제한다. "나중에 채운다"는 안 채워진다. 단 **순수 장식 이미지는 `alt=""`가 올바른 처리**다(스크린리더 건너뜀) — 콘텐츠 이미지와 구분할 것.
- 한글 slug 금지 → ASCII 정규화 (05 부록 D-3).
- `service_role`·R2 Secret을 `NEXT_PUBLIC_`으로 노출 금지.
- 검증 없이 다음 STEP 진행 금지. 실패 시 멈추고 원인부터.
- **DB 이관 후 "코드 생성기·추출기" 재실행 금지.** 정적 HTML→`data/*.ts` 추출기(예: bs4 파서) 류는 콘텐츠가 Supabase로 이관된 뒤 다시 돌리면 **자동생성 파일을 통째로 덮어써서 이후 수동 보강분(이미지 경로 등)이 소실**된다. 이관 완료 시점에 해당 스크립트는 폐기하거나 "실행 금지" 주석을 파일 상단에 박아라.
- **dev 서버를 켠 채로 프로덕션 빌드(`npm run build`) 금지.** 같은 `.next` 디렉터리를 두 프로세스가 공유해 `MODULE_NOT_FOUND` 500이 난다. 빌드 후엔 dev를 재시작할 것. (증상이 코드 버그처럼 보여 엉뚱한 곳을 파게 된다 — 복구는 `.next` 삭제 후 재시작)
